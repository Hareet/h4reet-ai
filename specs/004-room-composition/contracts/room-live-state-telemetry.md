# Contract: the room's telemetry, and the "Room live state" panel

Spec 004: FR-071, FR-072, and SC-014; Amendments A2, A3, B7, and C11; the Principle II deviation in spec 004's Assumptions. Plan: [plan.md](../plan.md). Research: [research.md](../research.md). Data: [data-model.md](../data-model.md). Related contracts: [tier-signal.md](tier-signal.md) (the live configuration, and the relay series of its §7), [serving.md](serving.md) (the `.glb.gz` copies), and [lookdev.md](lookdev.md) (the drafts log).

The intent: "The dashboard gets a panel, and the room's status polls get a disclosure entry."

The room adds no event kind, beacon, browser span, or alert:
- selecting a piece sends spec 002's existing event (§2);
- a studio model's load sends spec 003's asset event, once spec 001 carries it (§3);
- the "Room live state" panel reads the relay's own series (§4, §5).

No visitor's tier or cost is ever reported: both stay in the page (FR-047).

## 2. Selecting a piece: `object_selected`, unchanged (FR-071, B7)

- **One path.** Every input (the 3D pick, the 2D pick, and the "In the room" list) goes through `selectObject(id)`. It sends `{"kind": "object_selected", "id": "<the selectable's ID>"}` to `/api/room/events` with `navigator.sendBeacon`, then runs the selectable's action. Nothing else goes in the body, and a failed beacon is dropped (spec 002's room-events contract §1, on `feat/002-us6-events`).
- **The ID is the selectable's permanent ID** (FR-004): `laptop` for the laptop, its stand, and the monitor alike, and `chalkboard` beside `snowboard` and `bicycle` (B3). A retarget keeps the ID, so its series continues.
- **The events file.** `config/room-events.yaml` keeps its exact shape, `{schema: 1, kinds, objects, items}`. `objects` is the selectables' IDs in scene order, at most 64, generated by the compositor and committed, and `make test` fails while it's stale (B7). The gateway reads it at start, so an added selectable's events are accepted from the gateway's next start (User Story 1, scenario 2).
- **A removed selectable.** Its ID leaves `objects`, and the gateway refuses its events with 400 `id`. Its history stays on the dashboard for Prometheus's 30 days (spec 000's [telemetry.md §6.6](../../000-local-foundations/contracts/telemetry.md#66-prometheus-loki-and-grafana)), and the scene's `retired` list keeps the ID from ever naming anything else (FR-004).
- **The "Room" row, §7.8** (spec 002's, on `feat/002-us6-events`), needs no change: "Use per object per day" groups by `id`.

## 3. Studio models: spec 003's asset events, built and switched off (FR-071, C11)

When a studio model loads, retries, fails, or is skipped, the room's loader makes one event in spec 003's shape (its asset-events contract §1, on `feat/003-us5-comparison`):

| Field | The room fills it with |
|---|---|
| `asset` | spec 003's manifest `id` for the model: its record's file name without the extension, so each event is keyed by its record's file (FR-071) |
| `outcome` | `loaded`, once the model is swapped in; `retried`, when the first attempt failed and the one retry starts; `failed`, when the retry failed too and the stand-in stays (FR-057); `skipped`, below ADR 0010's capability floor, over the 96 MB texture ledger, or with the room already in 2D |
| `ms_bucket` | the time from the first fetch's start to the swap or the failure: `<250`, `<1000`, `<3000`, `<10000`, or `>=10000`; `<250` for a skip |
| `bytes` | for `loaded`, the size of the `.glb.gz` copy the site sends, which is the bundle's byte count for the model (C11); 0 otherwise |
| `mode` | `full`, `reduced`, or `2d`: spec 003's names, with the visit's `3d` mode reading `full` |

- **The queue.** Events wait in page memory, at most 64 of them; a full queue drops new ones, and the queue goes with the page.
- **While `live.asset_events` is `off`**, the default and the state until spec 001, the queue is never sent. A drafts build also shows each event in the lookdev page's log. No request is made.
- **Once it is `site`**, in spec 001's change, with row `V6` (the live configuration's RL3, [tier-signal.md](tier-signal.md) §1), spec 003's batcher drains the queue as its contract §1 says: at most one `POST /api/events` every 10 seconds, one `navigator.sendBeacon` when the page hides, and at most 20 events in each. A failed send is dropped, never retried or stored.
- **The relay's side** (admission, `h4.assets.events{asset, outcome, mode}`, `h4.assets.bytes{asset}`, and the "Assets" panel) is spec 003's and spec 001's. This spec adds none of it.
- **No `mode` event of the room's own.** Spec 002's `mode_2d` usage event already counts the fall to 2D.

## 4. The relay's series the panel reads (Amendment A2)

Spec 001's relay emits them; [tier-signal.md](tier-signal.md) §7 sets them out with their OTel names. In Prometheus:

| Series | Labels the panel uses | What it counts |
|---|---|---|
| `h4_relay_requests_total` | `h4_relay_route`: `hello`, `status`, `other` | every request the relay answers, on both listeners |
| `h4_relay_cap_refusals_total` | `h4_relay_route`; and `h4_cap_limit`, whose status value is `status_per_minute` | the cap's 429s |
| `h4_relay_status_class` | `h4_class`: `local`, `cloud`, `resting`, `budget`, `unavailable`, `unknown` | one-hot: the class FR-041's rows 5, 6, 8, 9, and 10 give the status the relay would answer now |

- **What a status count holds.** Every `GET /api/status` the relay answers: the room's polls, at most 2 a minute per visible, unpaused room; the `/status/` page's, every 60 s while it's visible; the snapshot sink's reads on the internal listener (spec 001's public-view contract §2); and probes. **The room's polls and the `/status/` page's can't be told apart** (FR-072). Both are anonymous same-origin reads of one path, and the room adds nothing that would mark its own.
- **The class is the relay's view, not a room's.** A room's own rows (the live source, pause, a failed or stale request, a fallback reply) aren't in it. So the panel shows what a fresh answer would make a room show, not what any one room showed.
- **Traces.** A non-error status request makes no trace (A2), so these series are the only record of the polls.
- **The public view (A3).** Spec 001's `local.requests_5m` counts hello only, as `h4_relay_requests_total{h4_relay_route="hello"}`, so the room's polls don't inflate the public request count (spec 001's public-view contract §3, on `spec/001-cloud-elevation`). §7.9's panel descriptions don't start with `[public]`, so the public view's publisher never reads them.
- **Proposed names.** If spec 001 renames a series, §7.9 changes and nothing else does: `deploy/scripts/test_dashboard.py` reads the panels' queries from `telemetry.md`.

## 5. `telemetry.md` §7.9, written now

Spec 000's telemetry contract, `specs/000-local-foundations/contracts/telemetry.md`, gains this section after §7.8 and before §8. It lands in `feat/004-setup`, on `feat/002-us6-events`, where §7.8 exists. The text, exactly:

```markdown
### 7.9 Room live state (spec 004)

The row's title is "Room live state": the status requests behind the room's laptop, and the class of the tier the relay's status would show now (spec 004, FR-072 and SC-014; its contracts/room-live-state-telemetry.md). The series are spec 001's relay's, as spec 004's Amendment A2 amends its contracts/relay-http.md §10: `h4_relay_requests_total` and `h4_relay_cap_refusals_total` gain the label `h4_relay_route` (`hello`, `status`, or `other`), the status bucket's refusals carry `h4_cap_limit="status_per_minute"`, and the one-hot gauge `h4_relay_status_class` reports, by `h4_class`, the class FR-041's table gives the status the relay would answer now: `local`, `cloud`, `resting`, `budget`, `unavailable`, or `unknown`. Until spec 001's relay emits them, this section is in `deploy/scripts/test_dashboard.py`'s `SECTIONS` but not in its `REQUIRED`, and the dashboard has none of its panels. The change that switches the room's live source on adds the panels and makes the section required. The row sits right below "Room".

| Panel | Type | Query |
|---|---|---|
| Status requests a minute (FR-072) | time series | `sum(rate(h4_relay_requests_total{h4_relay_route="status"}[$__rate_interval])) * 60` |
| Status 429s a minute (FR-072) | time series | `sum(rate(h4_relay_cap_refusals_total{h4_relay_route="status"}[$__rate_interval])) * 60` |
| Time in each class (FR-072, SC-014) | bar chart | `avg by (h4_class) (avg_over_time(h4_relay_status_class[$__range]))` |

- **Status requests** are every `GET /api/status` the relay answers, on both listeners: the room's polls, at most 2 a minute per visible, unpaused room; the `/status/` page's, every 60 s while it's visible; the snapshot sink's reads; and probes. The room's polls and the `/status/` page's can't be told apart, and both panels' descriptions say so.
- **The 429s** are the status bucket's, `status_per_minute`: 30 a minute with a burst of 10, per address, shared by every visitor behind one address. A refused poll leaves that room's laptop at unknown until its next answer.
- **Time in each class** is the share of the range the gauge spent at 1 in each class, read once at the range's end. It's the relay's view: a room's own rows (the live source, pause, a failed or stale request, a fallback reply) aren't in it.
```

How `test_dashboard.py` reads it: each table row is one panel, its title without the FR note, its type, and its query; the types are ones the test knows (`time series`, `bar chart`); each query cell holds one query with brackets, so the parse finds it; and every metric name is in the contract's text.

## 7. Until spec 001: what is measured, and where

Spec 004 names this deviation from Principle II and from step 7 of the [constitution](../../../.specify/memory/constitution.md)'s workflow ("A feature without a graph is not done"). Until spec 001's relay carries spec 003's asset events and serves the status, the room's piece loads and the "Room live state" panel have no production series. Until then:
- the piece loads are measured in tests (§9) and in the Author's lookdev runs, whose log holds each asset event;
- the polls are measured in tests, and in a drafts build's frame log ([tier-signal.md](tier-signal.md) §6);
- the room's bytes are measured by the compositor's report in each merge-request note that changes the room (FR-073).

The Author is the only visitor until publication (ADR 0013), and the deviation ends when spec 001 carries both.

## 8. Cost and data flow

- **Cost.** Three relay series of bounded cardinality: three route values, six classes, and the cap's limit names. The asset events, once on, are spec 003's: at most one request every 10 seconds while models load.
- **Data flow.** None new now. Once on, the asset events are row `V6`'s (spec 003's FR-040b); selecting a piece is spec 002's `V4` event; the status polls are `V7`'s, with A4's words ([tier-signal.md](tier-signal.md) §7).
