## The cause, as confirmed in the code

- `infra/prod/tunnel-end.tf:151-157` (base): the private group's only 8080 rule, `prefix_list_ids = [data.aws_ec2_managed_prefix_list.cloudfront.id]`, at line 156; the list is `com.amazonaws.global.cloudfront.origin-facing` (`tunnel-end.tf:92-95`). The comment above the group (`:142`) says "from CloudFront's VPC origin alone", but nothing in the group names the VPC origin's own group.
- A VPC origin reaches its target through the interfaces CloudFront makes in the target's subnet, which carry `CloudFront-VPCOrigins-Service-SG` and the subnet's private addresses, not the origin-facing list's public ones. The deploy showed it: `/api/*` didn't reach the relay until the Author added 8080 from that group by hand (`sgr-0aa7b8f4927baa380`). W1's reading of AWS's guide (plan.md §16 item 5; W1's note, B-6, "Superseded") took the prefix list as enough, and kept the group's rule as a fallback (tasks.md T176). The deploy needed the fallback.
- The group's rules are inline `ingress` blocks (`tunnel-end.tf:146-185`), which Terraform holds as the group's whole set: the next prod plan after a refresh shows the hand rule removed, and the apply removes it. That is the outage F1 prevents.
- The existing tests encoded the cause: `infra/test/test_prod_network.py::check_groups` held the private group to exactly 8080 from the prefix list, 5432 and 2301 from EC2's group, and `infra/test/test_prod_cdn.py::test_w1_makes_the_vpc_origin_and_nothing_else_of_the_relays_path` required any block naming `VPCOrigins` to sit behind the switch (W1's "the fallback … behind the switch"). The RED commit changes both assertions to the design below. Neither is a fix-task test file under the hook (no `FIX_TASK`); both edits are in the RED commit, none in GREEN.

## Does the prefix-list rule still serve anything?

**No.** By the CDN's origins as `infra/prod/` writes them (`edge.tf:101-120`), the distribution has two: `site`, the S3 bucket through origin access control, which never touches the tunnel end; and `relay`, the VPC origin `aws_cloudfront_vpc_origin.relay` (`edge.tf:72-90`), whose traffic arrives from the service group. No custom origin points at either of the tunnel end's addresses. The private interface, `10.42.1.10`, has no public address, and its subnet has no route out (`network.tf:63-70`), so no packet from the origin-facing list's public ranges can reach it at all. The rule admits nothing that could arrive. The deploy is the evidence: with it alone, `/api/*` didn't reach the relay.

**Kept in F1 all the same,** by his words for the plan: "prod's should show the security group rule and nothing he didn't do by hand". Dropping it would add a removal he didn't make. It is harmless, and `tools/gates/infra_policy.py`'s T7 still allows it ("8080 from CloudFront's origin-facing prefix list"). Its removal is a question on the morning page (Q-F1-1, below), recommended as its own change once F is applied and `/api/status` is seen answering through the service group's rule alone.

## Options, and the choice

| Option | What | Why not, or why |
|---|---|---|
| **A, chosen** | A data source, `data.aws_security_group.cloudfront_vpc_origins`, by `name = "CloudFront-VPCOrigins-Service-SG"` and `vpc_id = aws_vpc.prod.id`, with `depends_on = [aws_cloudfront_vpc_origin.relay]`; a second inline 8080 ingress in `aws_security_group.tunnel_end_private` from `[data.aws_security_group.cloudfront_vpc_origins.id]` | His order's form. The rule is the one he added by hand, so the plan shows nothing else of the group. The `depends_on` matters on a rebuild from nothing: CloudFront makes the group only once an origin exists, and a data source that finds nothing fails the plan. With it, the read waits for the apply whenever the origin has a change pending, and is made at plan time otherwise (as tomorrow). |
| B | 8080 from the private subnet's CIDR, `10.42.1.0/24` | No lookup, but it admits anything in the subnet, and the plan would show his rule removed and another one added: something he didn't do by hand. |
| C | The group's ID as a literal | Breaks on a rebuild, puts an account resource's ID in the repo, and isn't the data source he asked for. |
| D | A separate `aws_vpc_security_group_ingress_rule` | Inline and separate rules on one group fight: each apply of the inline set removes the separate rule. `check_groups` already refuses rules outside the group's own blocks. |
| E | The data source behind `local.wired`, as W1's test asked | `wired` is `true` from W2, for good. With `false`, the rule would have no source and AWS would refuse it. The `depends_on` covers the case W1's switch was for. |

**No replace.** `aws_security_group`'s `name`, `description`, and `vpc_id` force a new group, and the private group's interface holds it. All three stay byte for byte as applied. The description's "8080 from the CloudFront origin-facing addresses" is now half the story, and it stays that way: a word changed there would replace the group. A new test pins all three, with a fixture that changes the description. An inline rule added or removed is an in-place update.

**What the plan shows for the rule,** from a fresh clone, after the refresh reads his hand rule into the state:
- if his rule's description is the codified one, `The relay edge listener, from the CloudFront VPC origins group`, **nothing** for the group: config and state agree;
- otherwise, `aws_security_group.tunnel_end_private` **updated in place** (`~`), its `ingress` set showing one element for 8080 from the service group removed (his description) and one added (the codified one), and no `forces replacement`. The provider revokes the old element, then authorizes the new one, so `/api/*` may miss for a moment during that apply. Setting the hand rule's description to the codified text in the console before the plan avoids it (his step 1, below).
- if the plan also replaces the tunnel end (a host-file change from another F item), the VPC origin's target changes with it, the data source's read waits for the apply, and the `ingress` set reads `(known after apply)`. That is still in place, not a replace.

Anything else on the group, above all `forces replacement` or `-/+`, is a stop: record it and ask.
