## The cause, as confirmed in the code

1. **No wait.** `AdminOnlyStack.start()` (`scripts/operator.py:1747-1764` at the base) runs `docker compose … up -d --wait --no-deps gateway edge`, then `docker compose … run -d --rm … --name h4reet-prod-tunnel-admin tunnel admin`, and returns once `run -d` has *started* the container. `shared_command` (`scripts/operator.py:1842-1847`) then calls `AdminClient("prod").status()` at once. The tunnel's client (`deploy/tunnel/entrypoint.sh:95-116`) only starts ssh at that point. `deploy/tunnel/ssh_config_admin:19` gives the connection `ConnectTimeout 10`, and a failed try backs off 1, 2, 5, 10, 30 s. The forward `tunnel:5432` exists only once ssh is up, which ssh's `LocalCommand` marks by writing `/run/tunnel/connected` (`ssh_config_admin:29-30`, `entrypoint.sh:123`). The gateway, started first, found no store and retries every 5 s (`services/gateway/src/meter/store.ts:13-14,27`). So its `/admin/status` reads `"store": "unreachable"` (`services/gateway/src/routes/admin.ts:762-771`, `core/gateway.ts:683`), and `init` refuses an unreachable store.
2. **The wrong image.** The gateway's image is `h4reet-gateway:${H4_REF:-working-tree}` (`deploy/compose.yaml:134`, `pull_policy: never`). Prod's own compose call gives it `H4_REF` from prod's run file, `~/.local/state/h4reet/prod/run.env`, which it passes as a second `--env-file` (`Makefile:50,53`). That run file is written by `deploy/scripts/export_tree.py:267-278` and names the commit whose image `deploy/scripts/gateway_image.py:116` built as `h4reet-gateway:<commit>`. The admin-only stack passes `prod.env` alone (`scripts/operator.py:1727-1738`), and its environment holds only `PATH`, `HOME`, `DOCKER_*`, `H4_TREE` and the two empty tokens (`:1739-1744`), so `H4_REF` is unset. Compose falls back to `working-tree`, a tag that only dev-cpu builds, on the agents' engine (`Makefile:371-373`). On his engine that image doesn't exist unless he re-tags one.

## Options and the choice

**The wait.**
- (a) A fixed sleep, as he did by hand (20 s). Rejected: too long when the tunnel is quick, too short when the first ssh try times out (10 s) and the retry waits 1 s more.
- (b) Poll the tunnel's `connected` mark alone. That's needed, but not enough: when the mark appears, the gateway's last store attempt may have failed a moment earlier, and its next one is up to 5 s away. The first admin call can still read `unreachable`.
- (c) Poll the store alone, through the gateway. It works, but a tunnel that never connects only shows up as "store unreachable" after the whole bound, which says nothing about the cause.
- **Chosen: (b) then the store, each within its own bound.** The bounds are named in `scripts/operator.py`:
  - `ADMIN_TUNNEL_WAIT_S = 60`: up to 60 s for `/run/tunnel/connected` in `h4reet-prod-tunnel-admin`. That covers the first try's `ConnectTimeout 10` plus three more tries with the 1, 2, 5 s backoff: 10+1+10+2+10+5+10 = 48 s.
  - `ADMIN_STORE_WAIT_S = 20`: then up to 20 s until the gateway's own `/health` reads `store` as anything but `unreachable`. That is four of the gateway's 5 s retries, and the 20 s he waited by hand.
  - `ADMIN_POLL_S = 1` between tries.

  Each probe is one `docker` call through `run_docker`, so the tests use a fake tunnel and gateway, and no probe opens a port on the host. The tunnel probe is `docker exec h4reet-prod-tunnel-admin test -f /run/tunnel/connected`. The store probe is `docker compose … exec -T gateway node -e …`: it fetches `http://127.0.0.1:8080/health` inside the gateway's container, as compose's own health check does with `/health/live`, and exits 0 when `store` is `ok` or `uninitialized`. `uninitialized` counts as ready, because it is what `init` needs.

  When a bound runs out, `start()` raises `StackProblem`. The message says which wait failed and for how long: the tunnel's mark, or the store after the mark. `shared_command`'s `finally` still stops the stack, and the CLI exits 4.
- **The store probe in the CLI's own client, rejected.** Polling `/admin/status` from `shared_command` would add requests that every action's own stub listener would have to answer, and would read prod's token once per try. The probe inside the gateway's container needs no token.

**The image.**
- (a) Pass prod's run file as a second `--env-file`, as `Makefile:53` does. The trouble is that the run file also holds `H4_TREE`, the export's path, which the stack's own `H4_TREE` then silently overrides, because compose ranks the environment above env files.
- (b) Build or tag an image. Rejected: that is `make up`'s job (`gateway_image.py`), and the admin-only stack must never build.
- **Chosen: read the run file, refuse unless its `H4_REF` is a full commit SHA, and set `H4_REF` in the stack's environment.** Compose then resolves the gateway's image exactly as prod's compose names it: `h4reet-gateway:${H4_REF:-working-tree}` → `h4reet-gateway:<prod's commit>`, still `pull_policy: never`. The run file is read in `AdminOnlyStack.__init__`, before anything starts:
  - a missing run file is refused with `make up ENV=prod`'s name, since that writes it;
  - a malformed `H4_REF` is refused as malformed.

  `AdminOnlyStack(root, env_file, run_file=None)`: `None` means `~/.local/state/h4reet/prod/run.env`, so `shared_command`'s call stays as it was. When `up` fails, the message now names the image and how to get it (`make up ENV=prod` builds it). That is the case where prod's commit's image was pruned from his engine.
- **Left as it is: the tree.** The stack still binds this checkout's `deploy/edge`, `config` and compose file (`H4_TREE=root`), not the export of prod's commit. That is what contracts/shared-state.md §7 and the code's comment ("The tree's own files") say. Moving it would change more than the item names, so it goes on the page as a question (Q-F5-2).

## Tests (`scripts/test_operator_admin_stack.py`)

There is no container. A fake `docker` stands in for `run_docker`: it answers `run`, `up`, and `rm`, and plays the tunnel (its mark appears after N probes, or never) and the gateway (its store reads `unreachable` for M probes, then `ok` or `uninitialized`). A fake clock advances on each `sleep`.

1. The gateway's image is prod's own: the stack's environment holds the run file's `H4_REF`. `deploy/compose.yaml`'s gateway image, interpolated with that environment, is `h4reet-gateway:<the run file's commit>`, never `working-tree`.
2. No run file, or one whose `H4_REF` isn't 40 hex: `StackProblem` at construction, naming the file and `make up ENV=prod`, and no docker call.
3. `start()` asks nothing of the gateway until the tunnel's mark is there: the store probe comes only after the tunnel probe has succeeded, and `start()` returns only after the store reads.
4. It waits through a slow first connection (mark on the 15th probe), then through the gateway's retry (store `unreachable` for 4 probes, then `ok`).
5. An uninitialized store counts as ready, so `init` can run.
6. A tunnel that never connects: `StackProblem` naming the tunnel's mark and 60 s, after no more than `ADMIN_TUNNEL_WAIT_S` of the fake clock, with no store probe.
7. A store that stays unreachable after the mark: `StackProblem` naming the store and 20 s.
8. The bounds are named constants with the values above.
9. Through the CLI (`main(["--stack", "shared", "status"])`), with the real `AdminOnlyStack`, the fake docker, and a stub admin listener: the one status request comes after the tunnel's mark and the store's read, and the stack is stopped after it. A tunnel that never connects exits 4 with the stack stopped and no request to the listener.
