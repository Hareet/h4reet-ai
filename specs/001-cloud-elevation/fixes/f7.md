## Part 1: "Serving: Unknown", and the relay's `"ec2":"unknown"`

Two causes, independent of each other.

**The panel's.** The room's panel reads the tier signal, never the relay's `ec2`. The scene's live source is off, `apps/web/room/scene.yaml:25` (`live: { source: off, … }`), so `reduceTier` stops at row 1, `not-live` (`apps/web/src/room/signals/tier.ts:89`), and the room makes no status request at all (spec 004 FR-045). The panel's stat maps every tier outside its five words to `unknown` (`apps/web/src/room/hud/stats.ts:21`), and `stat.tier.unknown` is "Unknown" (`apps/web/room/ui-words.yaml:106`). So the panel reads "Unknown" whatever the relay says, and would read it with my fix too. Night 4's reading stands: it is the live source being off, as designed until a change switches it on.

Switching it on is spec 004's FR-045 and FR-074: "THE LIVE SOURCE SHALL be switched on only in the change that serves `GET /api/status` on the room's origin (spec 001), together with the disclosure change of FR-074", and FR-074: "IF the room would poll without that row, THEN it SHALL NOT be deployed." Spec 001 served the status, but no task of spec 001 switched the source on, and doing it needs three things this item shouldn't decide for him:
- **a new flow from every visitor's browser**, a status request every 30 s, which the disclosure's status row must describe first (V6 today: "a visitor calls hello or opens the status");
- **the row IDs disagree:** the compositor's rule RL2 (`apps/web/build/room/checks/rl.ts`, spec 004's `contracts/room-data-files.md` §13.9) wants the status row at `V7`, by Amendment A7's planned renumbering, but spec 001 wrote it as `V6`, and `V7` is Route 53's lookup. With `source: site` the build refuses until one of them changes: a spec 004 contract amendment;
- `apps/web/test/manifest.test.ts:149` holds the repository's live source to `off`.

So this part leaves the panel alone and puts the switch on the morning page (Q-F7-1), recommended as its own item after F. **My fix changes the relay's cause alone.**

**The relay's.** `GET /api/status`'s `ec2` comes from `deps.ec2State`, defaulting to `"unknown"` (`services/relay/src/app.ts:99`), and nothing supplies it: `assemble` builds the deps without it (`services/relay/src/start.ts:79-90`). The deps' own comment says why: "group 10's sink brings it, and until then the relay says `unknown`" (`app.ts:68-70`); group 10 built the sink, and the wire was never made. So the relay says `unknown` always, whatever EC2 does.

**Options.** The contract's source is "the sink's last read (contracts/public-view.md §2), at most 2 minutes old" (contracts/relay-http.md §6). The sink's host write (`h4-snapshot-sink.service`, root, the instance role) reads EC2 with `ec2:DescribeInstances` every 2 minutes and keeps the merged document in `/var/lib/h4reet/snapshot/latest.json` (`deploy/scripts/snapshot_sink.py:975-979`), before its put, so a failed put still keeps it.
- A. **The relay reads that document**, mounted read-only from the tunnel end's host, at most once in 5 s, as its status reads the store; `unknown` when it is missing, unreadable, not schema 1, or older than its bound. The contract's own source, no new endpoint, no credential. Its cost: a bind outside the gate's bind roots, so `tools/gates/compose_policy.py`'s `SERVICE_BINDS` gains the relay's one read-only bind: a patch for his hand.
- B. A new route on the sink container or the relay for the host write to push EC2's state: a new write path into a public-facing service, for one field.
- C. The relay infers it from its own checks (EC2 healthy, so `running`): no change outside the relay, but it can't say `stopped`, `pending`, or `interrupted`, and departs from the contract's source.

**Choice: A.** It is the contract's source, it reads a file the host already writes, and it adds nothing a visitor can reach. The bound: the write runs every 2 minutes and its run is stated as 30 s (contracts/public-view.md §1, "60 + 30 + 120 + 60"), and the file is replaced when a run ends, so a reader sees it up to 150 s after its `serving.taken_at`: the relay takes 150 s, so a healthy write never flaps to `unknown`, and a write that stops shows `unknown` within 2.5 minutes. The contract's row says so (relay-http.md §6, amended in this branch). The bind is `create_host_path`, so a fresh tunnel end's relay starts before the sink's first write and reads `unknown` until it.

**Files.** `services/relay/src/ec2state.ts` (new: the document's reading and its 5 s cache), `services/relay/src/start.ts` (`assemble` takes it, the document by default), `services/relay/src/app.ts` (the comment), `deploy/compose.yaml` (the relay's bind), `specs/001-cloud-elevation/contracts/relay-http.md` (§6's row). The patch for his hand: `tools/gates/compose_policy.py` and its test, `docs/merge-requests/human-patches/2026-11-17-f7-relay-snapshot-bind.patch`.

**Tests.** `services/relay/test/ec2-state.test.ts` (new): the document's state when fresh, `unknown` when stale, ahead, missing, unreadable, or off its schema, the 5 s cache, and the status's `ec2` from it through `assemble`. `deploy/scripts/test_compose_env.py`: the relay's binds are budgets and the snapshot folder, read-only, at the path the relay reads (the existing exact-list assertion, changed in RED).

## Part 3: the shared state's health check, as `postgres`

**Cause.** `deploy/compose.yaml:864` runs `pg_isready --host=/var/run/postgresql --username=postgres` with Docker's exec user, root; `deploy/shared-state/pg_hba.conf`'s one local line is `local all postgres peer`, so the server refuses root's peer identity as `postgres` and logs `FATAL: Peer authentication failed` on every 5 s check (the check itself passes: `pg_isready` counts a refusal as an answer).

**Options.** A health line in `pg_hba.conf` or a `pg_ident.conf` map from root to postgres would widen the store's local auth; Compose's health check has no `user`. **Choice:** step down to `postgres` with the image's own tool, the one its entrypoint uses (`gosu` in the newer official images, `su-exec` in the older Alpine ones; whichever the image has), in `CMD-SHELL`, as valkey's and seaweedfs's checks already use the shell. The container already holds `SETUID` and `SETGID` for its entrypoint's own step-down, under `no-new-privileges`, which a step-down by a root process doesn't need. I couldn't confirm which of the two the pinned image holds (the agents' engine wasn't configured for this session, and the bash gate refuses a fetch of the image's Dockerfile: Q-F7-3), so the line takes either; his morning check confirms it healthy and the log quiet.

**Files.** `deploy/compose.yaml` (shared-state's `healthcheck` alone; `impl-f4` changes `tunnel`). **Tests.** `deploy/hosts/test_shared_state.py`: the check steps down to `postgres` before `pg_isready`, by `gosu` or `su-exec`, never as root (the existing exact assertion, changed in RED).
