## The cause, as confirmed in the code

- **The relay, the shared state, and the sink are Docker's published ports on the private address:** `deploy/compose.yaml:911` (`10.42.1.10:8080:8080`, the relay), `:846` (`10.42.1.10:5432:5432`), `:956` (`10.42.1.10:2301:8080`). With `"userland-proxy": false` (`deploy/hosts/tunnel-end/daemon.json:2`) each is a DNAT in Docker's `nat` prerouting, so a reply is a forwarded packet from the container's bridge address (`172.30.0.0/16`), routed before conntrack writes `10.42.1.10` back as its source at postrouting. A `from 10.42.1.10` rule never sees it, as his item says.
- **Main's table sends `10.42.0.0/24` out `ens6`:** the public interface, `10.42.0.10`, is on that subnet, so its connected route is `10.42.0.0/24 dev ens6`, and the host's default is `ens6`'s too (`deploy/hosts/tunnel-end/networkd/zz-h4-public-first.conf:3`, metric 100 under device 0's 512). CloudFront's VPC origin's interfaces are in `10.42.0.0/24`, so the relay's replies to them left `ens6` with the source `10.42.1.10`, which `ens6`'s source/dest check drops: the 30 s timeout.
- **The one route by `ens5` is EC2's:** `deploy/hosts/tunnel-end/networkd/zz-h4-ec2-route.conf:2-4`, `10.42.0.20/32` by `ens5`'s DHCP gateway (the review of 59dfdc4a, I1). Nothing else in the host's files routes by `ens5`, and nothing marks a packet: `deploy/hosts/tunnel-end/nftables.nft:16-23`, `inet h4reet`'s `prerouting`, accepts and drops alone.
- **What the host step can reach:** `deploy/scripts/deployer.py:85-89` (`HOST_STEPS`, the tunnel end's `shared_state.py prepare`, from the release's tree) runs at each start (`:654`), and a boot is a start of the last release (`:705-710`, `restart_cached`). `prepare` already installs units from `deploy/hosts/tunnel-end/release/` (`deploy/hosts/tunnel-end/shared_state.py:207-246`). The user data's files are `local.host_files` (`infra/prod/tunnel-end.tf:22-40`); a change to any of them changes `terraform_data.tunnel_end_host`'s SHA-256 and replaces the instance (`docs/runbooks/tunnel-end.md`, "An OS update, or a changed host file").

### 5432 and 2301 from EC2

EC2, `10.42.0.20` in the public subnet, connects to `10.42.1.10:5432` and `:2301`, so its packets arrive on `ens5`, and the replies are Docker's, as the relay's are. Main's table routes them by the most specific route, `zz-h4-ec2-route.conf`'s `10.42.0.20/32` by `ens5`, ahead of the connected `10.42.0.0/24 dev ens6`: **EC2's replies already leave by `ens5`**, which is why the shared state and the sink answered EC2 on the night of the deploy while CloudFront timed out. With this fix they meet the mark rule (priority 104) first, and table 105's default is `ens5` too: the same interface, by either route. So the host route stays, and is kept on purpose: the tunnel end's own new connections to EC2 (the relay to EC2's relay block, `10.42.0.20:8085`, and to its collector, `:4318`; contracts/env-cloud.md row `ec2-relay-block`) are outbound, carry no mark, and still need it to leave by `ens5`. Removing it would also be a host-file change, so a replace. The test's routing model holds all three (CloudFront's reply, EC2's two, the tunnel end's own to EC2) to `ens5`, and the tunnel's 2222 and the host's way out to `ens6`.

| | Path | Replace? | Why not, or why |
|---|---|---|---|
| A | His lines into the user data's files: the two rules in `nftables.nft`'s `inet h4reet prerouting`, first; a networkd drop-in under `local.host_files` for the route and the two rules | **Yes**: `terraform_data.tunnel_end_host`'s SHA-256 changes, so the instance, and possibly the VPC origin (`tunnel-end.md`, "Watch the VPC origin") | The literal form of his lines, but the path his item asks to avoid |
| B | A oneshot unit from the release's tree running his `ip route`/`ip rule` lines, and `nft insert` into `inet h4reet` | No | `inet h4reet` is deleted and made again whole whenever `h4-nftables.service` loads `nftables.nft`, which would drop inserted lines; and `ip rule` lines systemd-networkd didn't make are foreign to it (its `ManageForeignRoutingPolicyRules=` and `ManageForeignRoutes=` default to yes), so a reconfigure of `ens5` can remove them |
| **C** | **From the release's tree, by the deployer's host step:** the route and the two rules as a systemd-networkd drop-in for `ens5`, in `/etc/systemd/network/70-ens5.network.d/`, beside the user data's `zz-h4-ec2-route.conf`; the two marks in a table of their own, `inet h4reet_reply`, whose `prerouting` runs just before `inet h4reet`'s, loaded by a oneshot unit enabled for every boot | **No**: nothing under `local.host_files` changes, so `terraform_data.tunnel_end_host` keeps its SHA-256, and neither the instance nor the VPC origin plans a change | **Chosen.** It changes with a release, as his item prefers; networkd owns the route and the rules, so they are made at each boot and each reconfigure of `ens5`, and never removed as foreign; the marks' table is its own, so the user data's `nftables.nft` load leaves it whole, and its own file replaces it whole |

**His rules' order and priorities, kept:**

- The route: `default via 10.42.1.1 dev ens5 table 105` is `[Route] Gateway=_dhcp4`, `Table=105`, in `ens5`'s drop-in: `ens5`'s DHCP gateway, `10.42.1.1`, the private subnet's router, the same way `zz-h4-ec2-route.conf` names it.
- The rules: `fwmark 0x105 lookup 105` at priority 104, then `from 10.42.1.10 lookup 105` at 105, each a `[RoutingPolicyRule]` with his `Priority=`. The mark is written `FirewallMark=261`, 0x105 in decimal, since every systemd reads a decimal there; `ip rule` prints it `fwmark 0x105`.
- The marks: in `inet h4reet_reply`'s `prerouting`, `iifname "ens5" ct state new ct mark set 0x105`, then `iifname != "ens5" meta mark set ct mark`, in his order. Its hook's priority is `mangle - 1`, so the chain runs first, before `inet h4reet`'s own `prerouting` (`priority mangle`), as his "first" asks, and before Docker's DNAT (`dstnat`, -100) and the routing decision. A new connection on `ens5` (CloudFront's to 8080, EC2's to 5432 and 2301) carries the mark in its conntrack entry; its replies, which come from Docker's bridges and so not from `ens5`, take it as their packet mark and so table 105's route out `ens5`. The incoming leg, on `ens5`, never takes the mark, so its own route to the container stays main's.
- Not his `inet h4reet` itself: the user data's file owns that table, and putting the lines there is option A's replace. The difference is one table name; the packets' order through the hook is his.

**The reboot:** the drop-in is in `/etc`, on the root volume, so networkd makes the route and the rules at every boot, as soon as `ens5` has its lease; the unit, `h4-reply-route.service`, is enabled (`WantedBy=multi-user.target`) and ordered after `h4-nftables.service` and before `docker.service`, so the marks are in place before any published port takes a connection. The deployer's boot runs `prepare` again besides (a boot is a start), which finds every file the same and changes nothing.

**A rerun:** `prepare` writes the drop-in only when its text differs, and reloads networkd (`networkctl reload`, then `networkctl reconfigure ens5`, as the first boot's `runcmd` does) only then; networkd makes one rule per section whatever the number of runs. The table's file starts `table inet h4reet_reply` / `delete table inet h4reet_reply`, as `nftables.nft` does, so each load replaces it whole, in one transaction: one copy of each rule, and no moment without them. `prepare` restarts the unit at each run, so each release's file is the one loaded.

**A failure** (the drop-in or the table not installed, the unit not enabled or not started, networkd not reloaded) fails `prepare`, said on stderr, and so the start: a new release is rolled back, with `deploy_rolled_back`, rather than deployed with replies that time out. This is the store's rule for the host step ("A failed step is a failed start", `deployer.py:84`), not the sink's, whose failure is said and passed, since without these replies the site answers nothing.

**On the running tunnel end, the first release with this fix:** networkd configures `ens5` again, as the first boot's `runcmd` does, once: a connection through `ens5` may stall for the moment it takes (not measured here; his step 2 below reads the result). His in-memory lines then sit beside the fix's: the two rules and the route are the same as networkd's (which takes them over, or keeps its own beside them), and his two lines in `inet h4reet prerouting` mark what `inet h4reet_reply` has already marked, to the same value. Both are harmless, and the next reboot, or the next load of `nftables.nft`, leaves the fix's alone.

## The tests (`deploy/hosts/test_reply_route.py`)

- **What the step writes:** the drop-in's sections are exactly his route and his two rules, with his tables and priorities, the mark 0x105; the table's file holds exactly his two lines, in his order, in a chain hooked before `inet h4reet`'s; the unit loads that file, after the user data's filter and before Docker, and is enabled for boot. The drop-in's place is `ens5`'s directory, the one the user data's `zz-h4-ec2-route.conf` is in, and sorts after it.
- **`prepare` installs them** from the release's tree, enables and restarts the unit, reloads networkd and reconfigures `ens5`; a failure of any of those is a failed step.
- **A rerun adds no second rule:** a second `prepare` leaves one drop-in with the same text and reloads nothing; the table's file deletes its own table before it defines it, and the user data's file never names it, so neither load leaves two.
- **It holds after a reboot:** the defaults are under `/etc` (never `/run`, tmpfs); the unit is enabled with `WantedBy=multi-user.target`; and the deployer's boot runs the host step (`deployer.boot` → `restart_cached` → `start` → `host_step`), checked against the deployer's code.
- **The routing model,** from the files as written plus the routes the host has (the connected subnets, `ens6`'s default first, the user data's EC2 route): CloudFront's reply (from the relay's bridge, to `10.42.0.0/24`), EC2's replies on 5432 and 2301, and the tunnel end's own connection to EC2 leave by `ens5`; the laptop's tunnel's replies on 2222 and the host's way out leave by `ens6`; and without the fix's files, CloudFront's reply leaves by `ens6` (the night of the deploy) while EC2's leave by `ens5`.
- **No replace:** none of the three new files is under `local.host_files`, so the user data's SHA-256 is unchanged.
