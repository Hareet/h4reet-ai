## The cause, as confirmed in the code (at the base)

- `scripts/infra/shared_state.py:252` reads the CA's PEM, `ca_pem = ca_crt.read_text(...)`, several lines with their newlines.
- `scripts/infra/shared_state.py:261` puts it unchanged: `put(profile, CA_PARAMETER, ca_pem, "String", stage)`. The same function writes the laptop's `GATEWAY_DB_TLS_CA` as `base64.b64encode(ca_pem.encode()).decode()` at `:266`, so the laptop got the right form and the parameter got the other one.
- The parameter's readers are the two hosts' env templates: `deploy/hosts/ec2/ec2.env.example:35` (`GATEWAY_DB_TLS_CA=__PARAMETER:/h4reet/hosts/SHARED_STATE_TLS_CA__`) and `deploy/hosts/tunnel-end/tunnel-end.env.example:29` (`SHARED_STATE_TLS_CA=…`, which `deploy/compose.yaml:904` passes to the relay as `RELAY_DB_TLS_CA`).
- `deploy/scripts/write_env.py:44` `UNSAFE = re.compile(r"[\s$\"'`\\#]")`, used at `:133`: a value holding `\n` (or a space, which a PEM's subject line doesn't need but its newlines do) is outside the grammar, so `render` raises `Refused` for the key and nothing is written: neither host had an env file.
- Behind it, both readers decode base64: `services/gateway/src/meter/store.ts:159` `Buffer.from(env.GATEWAY_DB_TLS_CA ?? "", "base64").toString("utf8")`, then `PEM_CERTIFICATE` (`:92`); `services/relay/src/config.ts:143` `Buffer.from(caText, "base64").toString("utf8")`, then its own PEM pattern. A PEM given to either decodes to bytes that aren't a PEM, so even a grammar that let it through would leave `store_tls_required` and `RELAY_DB_TLS_CA must be the base64 of one PEM certificate`.
- The contracts already ask for base64: contracts/env-cloud.md's `GATEWAY_DB_TLS_CA` row says EC2's is "the same [base64 of its PEM on one line], from `/h4reet/hosts/SHARED_STATE_TLS_CA`". contracts/shared-state.md §3 named the parameter without its form; that gap is how the writer drifted.
- `--rotate` takes the same path (`:174` makes the new CA, then `:252` to `:269`), so it stored a rotated CA as PEM too.
- The existing test (`deploy/hosts/test_shared_state.py`, `test_tls_keeps_the_ca_in_the_terminal_…`) checks the three names and the env file's base64, never the parameter's value: the fake `aws` logs the argv, and the `file://` it names is gone by the time the test reads.

## Options

1. **The script stores base64 of the PEM** (chosen). One value, computed once, goes to the parameter and to the laptop's env file. It matches the contracts, both readers, the grammar, and what the Author wrote by hand (version 2), so the parameter as it stands is already right and nothing on the hosts changes: no release, no new host code.
2. The readers accept a PEM as well as base64, and `write_env.py` encodes the one parameter. Two TypeScript readers, a special case in the hosts' grammar, a release to both hosts, and a second form to keep right forever, to save one line in the writer. Refused.
3. Store both forms in two parameters. A second name to keep in step on every rotation, for no reader. Refused.

## The tests

`deploy/hosts/test_shared_state_ca.py`, beside `test_shared_state.py`, whose `terminal` fixture it repeats with a fake `aws` that also records the contents of each `file://` value it is given (the script deletes the file after the call, so the argv alone can't show it). Its tests run the real script in a scratch tree, outside the sandbox's variable, with openssl, and:

1. **The parameter is base64 of the CA's PEM on one line**, equal to the laptop's `GATEWAY_DB_TLS_CA`, and it decodes to `~/.config/h4reet-ai/shared-state/ca.crt` byte for byte.
2. **Both readers take it:** Node (the toolchain's) runs each reader's own decoding and pattern, read out of `store.ts` and `config.ts` (the test fails if either reader's decoding line changes, so it can't pass against a reader that no longer decodes this way), on the stored value: both say it is one PEM certificate.
3. **`write_env.py`'s grammar takes it:** `render` from `deploy/scripts/write_env.py`, on both hosts' real templates, with the stored value for the CA and plain values for every other name: no refusal, and the env files carry it unchanged as `GATEWAY_DB_TLS_CA` (EC2) and `SHARED_STATE_TLS_CA` (the tunnel end).
4. **`--rotate` is right:** a second run without it stores the same value; a run with it stores a different value, in the same form, which decodes to the new `ca.crt` and equals the laptop's new `GATEWAY_DB_TLS_CA`, and each passes 2 and 3.

The covering tests: `deploy/hosts/test_shared_state.py` (the script's other tests), `deploy/scripts/test_write_env.py`, `deploy/hosts/test_ec2_host.py` (unchanged files, run to show nothing else moved).

```bash
pf=h4reet-admin

  --query Parameter.Value --output text)

The fix touches neither `deploy/scripts/write_env.py` nor anything else the tunnel end's user data carries, and `scripts/infra/shared_state.py` runs in his terminal alone, so it plans no replace and needs no release.
