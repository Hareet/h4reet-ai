## The cause, as confirmed in the code

- `infra/parameters.txt:1-60` lists 46 names the hosts and the account's functions read. Only some have a writer:
  - `scripts/infra/tunnel_keys.py:202-223` (`make tunnel-keys`) writes eight: `/h4reet/tunnel-end/{HOST_KEY, AUTHORIZED_KEY, RELAY_TOKEN_LAPTOP, RELAY_TOKEN_EC2, SNAPSHOT_SINK_TOKEN, TELEMETRY_BLOCK_TOKEN}` and EC2's copies `/h4reet/ec2/{RELAY_TOKEN_SELF, SNAPSHOT_SINK_TOKEN}`;
  - `scripts/infra/shared_state.py:10-14` (`make shared-state-tls`) writes `/h4reet/hosts/SHARED_STATE_TLS_CA` (and the tunnel end's TLS key and certificate);
  - Terraform writes the two Strings `/h4reet/hosts/RELEASE_BUCKET` and `/h4reet/prod/tunnel-end-address`.
- The other 34 have no writer at all: group 7's 24 EC2 names (`infra/parameters.txt:33-60`), the relay's two role passwords (`:26-27`), the alert bridge's Telegram pair (`:8-9`), and the audit's allowlist (`:14`). `scripts/infra/secrets_check.py:7` and research.md R-26 (`research.md:584`) say the Author writes each "by hand … with `aws ssm put-parameter`"; `make secrets-check` (`Makefile:811-813`) only lists them.
- On a host, `deploy/scripts/write_env.py:117-120` refuses the whole env file while any expected name is missing (`missing in Parameter Store: …`), so the stack never starts: what the deploy hit, and what his one-off script filled.
- Two of the names can't be copied by their own name from the laptop's `prod.env`, and a naive copy gets them wrong:
  - `/h4reet/ec2/RELAY_TOKEN_SELF` is EC2's token, the tunnel end's `RELAY_TOKEN_EC2` (`tunnel_keys.py:217`); the laptop's `RELAY_TOKEN_SELF` is `RELAY_TOKEN_LAPTOP` (`tunnel_keys.py:238`). Copying it would let EC2 sign in to the relay as the laptop;
  - `/h4reet/ec2/DB_GATEWAY_PASSWORD` and `DB_GRAFANA_RO_PASSWORD` are the shared state's `gateway` and `grafana_ro` roles (`deploy/hosts/tunnel-end/shared_state.py:60-61`), which the laptop's file names `GATEWAY_DB_PASSWORD` and `GATEWAY_GRAFANA_RO_PASSWORD` (`deploy/hosts/ec2/ec2.env.example:36`, `GATEWAY_DB_PASSWORD=__PARAMETER:/h4reet/ec2/DB_GATEWAY_PASSWORD__`). Both hosts sign in as the same role, so the values must match.

## Options

1. **A runbook section with the `aws ssm put-parameter` lines.** No code, but values pass through his shell (history, `ps`) unless he writes each file by hand, and nothing checks "never `--overwrite`" or the mapping above. Rejected: it's the by-hand step the order replaces.
2. **Extend `make tunnel-keys` or `make secrets-check`.** `secrets-check` is read-only by design (its docstring, FR-009), and `impl-f7` changes it tonight; `tunnel-keys` makes keys and rotates them, a different lifecycle. Rejected: they would mix a writer into a reader, or a one-time fill into a rotation.
3. **A new Author-only target, `make secrets-fill [PROFILE=…]`, and its script `scripts/infra/secrets_fill.py`, beside `secrets-check`.** Chosen. It reads the expected names and types from `infra/parameters.txt` (so the names `impl-f7` adds there reach it with no change here), asks Parameter Store which exist (`describe-parameters`, names only, as `secrets-check` does), and writes each missing one once.

## The design

- **Author-only:** the target calls `AUTHOR_ONLY` as his others do, and the script refuses itself when `SANDBOX_RUNTIME=1` (exit 2) before any call. A named profile is required (`PROFILE=…` or `AWS_PROFILE`).
- **Which names:** each name in `infra/parameters.txt` that `describe-parameters` under `/h4reet/` doesn't return. A name that exists is never touched.
- **Never `--overwrite`:** `put-parameter` without `--overwrite`, so a name written meanwhile makes AWS refuse (`ParameterAlreadyExists`) rather than replace it; the script reports that name and goes on.
- **Not this target's, and why (printed, not written):** the tunnel's eight (`make tunnel-keys`: they come in pairs, the tunnel end's and EC2's or the laptop's, and a value made here alone would break the pair), the shared state's TLS (`make shared-state-tls`: the CA, and the tunnel end's key and certificate, which the list doesn't name yet), and Terraform's Strings (prod's and the account's applies: `RELEASE_BUCKET`, `tunnel-end-address`, and `ec2-instance-id`, which the list doesn't name). These keep their own writers (`OTHERS` in the script).
- **Where each value comes from, in the order's words:**
  1. **copied from `prod.env`** (`~/.config/h4reet-ai/env/prod.env`) where the laptop has the value: the key is the name's last part, except the two renames above (`DB_GATEWAY_PASSWORD` ← `GATEWAY_DB_PASSWORD`, `DB_GRAFANA_RO_PASSWORD` ← `GATEWAY_GRAFANA_RO_PASSWORD`). An empty value, `__ASK__`, or `__GENERATE__` is no value. The audit's allowlist comes from the laptop's `~/.config/h4reet-ai/infra/iam-allow.txt`, the file `infra/parameters.txt:11-13` names as its source;
  2. **generated in `init_env.py`'s shapes** otherwise: `init_env.generate()`, loaded by path, so the shapes stay in one place. The relay's two role passwords take `GATEWAY_DB_PASSWORD`'s shape (64 hex), the shape `init_env.py` gives every store password;
  3. **asked at a hidden prompt** when neither (`getpass`, echo off, on the terminal). Without a terminal (stdin not a tty) it refuses the run before any write, naming each name it would have asked for: nothing written. An empty answer skips that name; the rest are written.
  A missing `prod.env` refuses the run (exit 1, "make init-env ENV=prod first"), since generating a value the laptop already holds would split the shared state's `gateway` password between the hosts.
- **Values only through 0600 files:** every value goes to a file made with `mkstemp` (0600) in a fresh 0700 folder under `~/.config/h4reet-ai/` (which agents can't read), passed as `--value file://…`, and removed after the call; the folder is removed at the end. Nothing goes on a command line or into the environment.
- **Names printed, never values:** one line for each name the list expects, as `secrets-check` prints them: `<name> present`, `<name> wrote (<type>): copied from prod.env's <KEY>` (or `generated`, or `from the prompt`), `<name> missing; make tunnel-keys writes it, …` (or another writer), or `<name> not written: aws ssm put-parameter exited 254 (ParameterAlreadyExists); never overwritten` (AWS's error code alone, never its message). Then `secrets-fill: nothing to write` when there was nothing, and always `secrets-fill: <n> written, <n> not written, <n> left to their writers`. Exit codes: 0 nothing it fills left missing; 1 refused (no `prod.env`, no terminal for a prompt), or a name not written (refused by the store, or skipped at the prompt); 2 it couldn't run.
- **Order of work:** every value is gathered (prompts first), then the writes, so a refused prompt leaves no half-done set behind it.
