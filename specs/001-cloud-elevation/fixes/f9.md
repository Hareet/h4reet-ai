# Fix F9: a release never reconfigures the tunnel end's live private interface

Spec 001, a bug-fix found on the deployed site on 2026-11-18. Branch `fix/001-live-network`, from main `f1abe245` (F1 to F8 merged). The brief came from the Author's session; spec 001's `plan.md` indexes this file under "Bug-fixes, 2026-11-18".

## The evidence, as the brief gives it

On the tunnel end, release `20261118T001208Z-f1abe2454054`'s host step (`deploy/hosts/tunnel-end/shared_state.py prepare`, fix F2's part) wrote `zz-h4-reply-route.conf` into `/etc/systemd/network/70-ens5.network.d/`, then ran `networkctl reload` and `networkctl reconfigure ens5`. networkd's journal at 00:24:36Z:

```text
ens5: DHCPv4 address 10.42.1.10/24, gateway 10.42.1.1 acquired from 10.42.1.1
ens5: Could not set DHCPv4 route: Nexthop has invalid gateway. Network is unreachable
ens5: Failed
```

The same at 00:39 and 00:42, with the drop-in moved out (only the user data's `zz-h4-ec2-route.conf` beside ec2-net-utils' `/run/systemd/network/70-ens5.network`, plain `DHCP=yes`). At 00:58:14Z networkd retried by itself, "Failed to configure address: Numerical result out of range", and removed the rules added by hand (its default `ManageForeignRoutingPolicyRules=`/`ManageForeignRoutes=`). Docker then couldn't bind `10.42.1.10:5432` ("cannot assign requested address"); the shared state, the relay, and the sink didn't start; `deployments.jsonl` read `rollback_failed`; the site was down until the address, table 105's routes, and rules 104/105 were set by hand. After the instance's clean reboot at 14:15Z networkd configured `ens5` with the same drop-in: `routable (configured)`, `10.42.1.10 (DHCP4 via 10.42.1.1)`, table 105 `default via 10.42.1.1 dev ens5 proto dhcp metric 512`, rules 104/105 `proto static`.

## The cause, as confirmed in the code

- `deploy/hosts/tunnel-end/shared_state.py:269-273` at `f1abe245`: when the drop-in's text differed from the one on disk, `prepare` ran `networkctl reload` then `networkctl reconfigure ens5` on the running host. `reconfigure` drops and makes again everything networkd holds on the link, the DHCP address with it; on 2026-11-18 the making-again failed and left `ens5` `Failed`, with no IPv4.
- `deploy/scripts/deployer.py:654`: the host step runs before compose; it returned 0 (both `networkctl` calls only ask networkd), so compose started, and every port published on `10.42.1.10` failed to bind. The rollback, `restart_cached` (`:678`), ran the previous release's host step, which found the drop-in the same and changed nothing, and its compose failed the same way: `rollback_failed`.
- The drop-in itself is right: networkd made exactly its route and rules at the next boot. What fails is a live reconfigure. Why it fails live and not at boot (the hand-made rules and routes beside networkd's, the order of the lease's routes and table 105's, or something in systemd 252) isn't established here, with no host; the fix doesn't depend on it.

## The fix

`shared_state.py`'s new `reply_route`, which `prepare` calls where fix F2's lines were:

1. **The drop-in, read:** `live_plan` reads its sections; it knows a `[Route]` with `Gateway=_dhcp4` and `Table=`, and a `[RoutingPolicyRule]` with `From=` or `FirewallMark=`, `Table=`, `Priority=`. Any other key fails the step before anything changes, naming the key, so what's live never drifts from what networkd makes at boot.
2. **The address, before:** `ip -4 -o addr show dev ens5` must hold `inet 10.42.1.10/`; it waits up to 30 s, every 2 s, for a boot's lease. Missing: nothing of the network changes, stderr says so and points at the runbook, and the step fails.
3. **The marks' unit,** enabled and restarted, as F2 has it (nft only; it never touches an address).
4. **The drop-in, for the next boot:** written only when its text differs, through a temporary file and a rename. No reload, no reconfigure.
5. **What's live, as networkd made it at boot, only where it's missing:** table 105's default, if `ip -4 -j route show table 105` has none by `ens5`, from main's DHCP default by `ens5` (`ip -4 -j route show default dev ens5`): `ip -4 route replace default via 10.42.1.1 dev ens5 table 105 proto dhcp metric 512`; then each rule `ip -4 -j rule show` lacks: `ip -4 rule add from 10.42.1.10 table 105 priority 105 protocol static`, `ip -4 rule add fwmark 0x105 table 105 priority 104 protocol static`. The route goes first, so no rule points into an empty table. A rerun, or a boot where networkd made them, changes nothing.
6. **The address, after** (2 s after a change): gone, or any command failed, and the step undoes its own changes (the rules and the route it added deleted, a route it replaced put back, and a changed drop-in's old text written back; a drop-in that was missing before the step stays, since its text is right for the next boot and a rollback's step must find it unchanged, below), says so on stderr, and fails. The deployer's start fails with it before compose runs, so the running release's containers are left as they are (`deploy_rolled_back`).

The drop-in's text is unchanged, on purpose: the first release with this fix rolls back, if it must, to `f1abe245`'s host step, which still reloads networkd and reconfigures `ens5` when the drop-in on disk is missing or differs from its release's. It finds the same text and runs no `networkctl`. For the same reason an undo never removes the drop-in (the review of bd7e0765, nit 1): a step that wrote it where it was missing and then failed leaves it in place, so the rollback's step can't find it "changed". The one way left for that step to find it missing is a host where it never was, and F2's release wrote it; the Author's first morning check reads it before the release.

F2's backlog R-1 closes with it (a rerun makes any missing rule again, and a failure never leaves the drop-in different from both releases'), and R-2's other half goes (no `networkctl` left to measure).

## Done, and not done

**Done:** the host step never runs `networkctl` or restarts networkd; it writes the drop-in for the next boot and makes table 105 and the two rules live with `ip`, as networkd makes them at boot, only where missing; it checks `10.42.1.10` on `ens5` before (with a bounded wait) and after, and undoes its own changes and fails the step when the address is gone or a command fails. The runbook's T058 says the same and has an item for the night's symptom. Nothing else in the repository reconfigures networkd after the first boot.

**Not provable here:** no host, no networkd, no `ip`: the commands' text and iproute2's JSON are read from iproute2 and the Author's readings, not run. The model in `NetHost` is this session's reading of iproute2 (`ip -j` field names, `fwmark` as a hex string, the filtered `dev` left out). His step 2 reads the result; if a field name differs on Amazon Linux 2023, the step would add a rule that exists, `ip rule add` would answer `EEXIST`, the step would fail and undo, and the release would roll back with the site still serving: safe, and said.

## Backlog

At this branch's tip:

- **F9-1, `deploy/hosts/tunnel-end/shared_state.py` (`make_live`):** a rule or route the step made live, before networkd has read the new drop-in (the next boot), is foreign to networkd, which removes it if it next configures `ens5` (a carrier loss, say). Harmless today: the drop-in is unchanged by this fix, so networkd already holds it. If the drop-in ever changes, the release that changes it should be followed by a reboot inside the hours. And `make_live` only adds (the review of bd7e0765, nit 2): a future drop-in that drops a rule or route, or changes one, leaves the old one live beside the new until a reboot, when networkd makes only what the drop-in holds. Such a release should say so and be followed by a reboot, or the step should learn to delete what it made before.
- **F9-2, `deploy/hosts/tunnel-end/cloud-init.yaml.tftpl:21-23`:** the first boot's `networkctl reconfigure ens6` and `ens5`. Safe where they run (once, before anything binds), and changing them replaces the instance; worth dropping at the next replace if the drop-ins are already in place when networkd starts.
- **F9-3:** why a live reconfigure failed ("Nexthop has invalid gateway", then "Numerical result out of range") while the boot didn't. Not needed for the fix; worth a note in the incident's record if he reads it on a scratch instance.
