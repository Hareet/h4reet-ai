# F6: the release can't resume

Approved provisionally by the Author's order of 2026-11-16 (night 5).

His item, word for word (orders.md, night 5, F):

> 6. **The release can't resume** (`deploy/scripts/release.py`): a run that pushed the gateway and the room then refused leaves their commit tags in ECR, whose tags are immutable (`infra/account/registry.tf:10`), so the next run refuses. Make a rerun of the same commit safe (e.g. accept a tag whose digest the run would push, or tag by release id) without weakening "a release is of a gated merge"; tests.

Written by: impl-f6 (implementer), night of 2026-11-17 · Base: `f6baef8ce027dbffb4056a73c61b28d4625ffb18` · Branch: `night/impl-f6/impl-f6` · Spec: 001-cloud-elevation · Contract: `contracts/releases-deployer.md` §2

## The cause, as confirmed in the code

- `infra/account/registry.tf:10` and `:28`: every repository, the functions' and the stack's (`h4reet/<service>`), has `image_tag_mutability = "IMMUTABLE"`. Once a tag names an image, a push of another image under it is refused.
- `deploy/scripts/release.py:673`: each project image is tagged `ref = f"{opts.registry}/{repository}:{head}"`, the commit, which is the same on every run of that commit.
- `deploy/scripts/release.py:674-689`: `docker buildx build --push --tag <ref>` builds the image again on every run and pushes it to that tag; a push that fails is `Refused(f"{name}'s image didn't build")`, exit 1.
- A second build of the same export isn't byte-identical: each image's config has its build time, and buildx attaches a provenance attestation with the build's own times by default, so the index digest differs from run to run. So the rerun's push names a new digest under a tag ECR already holds for the first run's, and ECR refuses it. **To confirm** in his terminal: I read this from buildx's and ECR's documented behaviour; no agent can reach the registry.
- What can refuse after a push: in step 2 (`release.py:664-720`) the builds and the upstream copies interleave in the hosts' order, the gateway and the room first (EC2's), so any later build (the tunnel's, the relay's, the snapshot's) or copy that refuses, the site's sync (`:723-724`), or a bucket upload (`:759-780`) leaves the commit's tags behind.
- The upstream copies (`release.py:698-720`) are tagged with the lock line's own tag, the same on every release, and `imagetools create` puts the lock's very digest under it, so a rerun, or the next release with the same lock, puts an unchanged manifest under an existing tag. ECR's tag immutability refuses a tag moved to another image, and I expect it to accept an unchanged one. But the release depends on that without checking, and I haven't seen it happen: the item names only the builds' tags, and no agent can reach the registry. **To confirm** at his next release. The fix removes the dependence.

### Where "a release is of a gated merge" is enforced today

In `released()`, before anything is exported, built, or pushed:
1. `release.py:646`, `check_self`: the release and the makefiles are refs/heads/main's blobs (I2);
2. `release.py:647-649`: the commit is `refs/heads/main`'s, never the checkout's HEAD;
3. `release.py:650`, `check_gate` (`:299-325`): that commit is a merge whose message carries the gate's line for the tip it merged, reporting a pass (contract §2.1, I-H, nit 1);
4. `release.py:654`: everything after is built from `git archive` of that commit; with `--public`, `:656`, the red team's runs of it; `:657`, its site's check.

Every image the release records was built in that run, from that export, after those checks. release.json names the commit (`:742`) and the tree `trees/<commit>.tar.gz` (`:746`), which the first step and the deployers hold to the commit (contract §1, "The tree's key"). The deployers pull each project image by its digest from release.json (`deploy/scripts/deployer.py:255-272`, `:662-666`), never by its tag. Nothing in the repository reads an ECR tag of a project image (searched: `grep -rn 'h4reet/(gateway|web|tunnel|relay|snapshot)[:@]'` over deploy, services, infra, docs and specs finds none).

## Options

1. **Reuse the commit's tag when it exists**: inspect `<repo>:<commit>`, and if it's there, take its digest and skip the build. Reruns are fast and leave no extra images, and the existing tests stand. But the run would record an image it didn't build, on trust that only an earlier release run of this commit pushed that tag. The code can't check that: a label would be self-asserted, and a build pushed by hand under the commit's name (a laptop build with drafts, say) would be released. That widens "a release is of a gated merge" from "built by this run after its gate" to "found in the registry". Rejected.
2. **Accept the tag when it names the digest the run would push**, for the builds. This needs reproducible builds (`SOURCE_DATE_EPOCH`, `rewrite-timestamp`, no provenance, and npm installs that reproduce), on both platforms. Nothing here can show that, so a rerun might still refuse. Rejected for the builds. **Taken for the copies**, whose digest the run knows before it pushes (the lock's): a copy's tag that already names the lock's digest is accepted without a put, and one that names another digest still refuses.
3. **Tag each build by the release id** (`<time>-<commit's first 12>`, the id release.json already carries). Every run pushes under tags of its own, so a rerun never meets a tag an earlier run left. Every image recorded is still this run's own build, from the export, after the gate. **Chosen**, with option 2 for the copies.

The release id is taken once, at the start of step 2 (after every gate), and is the same in the tags, in `release.json`'s `release`, and in `releases/<id>/release.json`. So an ECR tag names the release that recorded it, and a tag with no `releases/<id>/` in the bucket is a run that refused.

**What it costs** (a question on the page, Q-F6-1): the stack's lifecycle rule (`registry.tf`, "Keep the newest ten tagged releases") counts images. Before, a commit's failed runs left at most one image per repository, since the next run refused. Now each run that refuses after a push leaves one per repository it pushed. Each takes a slot from the oldest release, the one a rollback reaches last. Ten such runs between two releases would expire the running release's images. A host that's running keeps its cached copy, but a replaced EC2 couldn't pull it. Nothing in this item changes the rule. The page recommends keeping it as it is and deleting a refused run's tags by hand when a night leaves more than two.

**Not widened**: the gate's three checks (`:646-650`) run before step 2 on every run, the rerun included, and the release id is taken after them. A tag that already names another image refuses as before. For a build, ECR refuses the push to an immutable tag and the release refuses at `:688`. For a copy, the release refuses unless the tag names the lock's digest after its put. The tests below show both, and that a rerun whose merge isn't gated refuses before anything is built.
