# F4: the laptop's tunnel reads its own key

Approved provisionally by the Author's order of 2026-11-16 (night 5).

His item, word for word (`orders.md`, F):

> 4. **The laptop's tunnel can't read its own key.** The `tunnel` service runs as `10001` (`deploy/compose.yaml`) and bind-mounts `H4_TUNNEL_DIR` read-only, which P22 requires to be 0700 and owned by him, so ssh found no host key ("Host key verification failed"). He worked round it with an ACL, since removed. Design the fix (e.g. the entrypoint copies the two files as root into its 0700 tmpfs, then drops to 10001; or the service runs as his uid) with P22 kept true; test it.

Spec 001, a bug-fix on the deployed W2 (base `f6baef8ce027`). Branch `night/impl-f4/impl-f4`. Spec 001's `plan.md` and `tasks.md` are left alone; the merge indexes this file there.

and `docs/runbooks/laptop.md:11`: "H4_TUNNEL_DIR isn't a folder only its owner can open", "id_ed25519 in H4_TUNNEL_DIR is missing or others can read it". P22 checks the modes; the owner is his because his `make tunnel-keys` makes the folder (`scripts/infra/tunnel_keys.py:190`, `mkdir(mode=0o700)`; `:231`, `chmod(client, 0o700)`) in his own terminal. Either way, the folder is one that only he, and root with a capability that bypasses file modes, can open.

## The cause, confirmed in the code

1. `deploy/compose.yaml:748`: the `tunnel` service runs as `user: "10001:10001"`, the image's `tunnel` user (`deploy/tunnel/Dockerfile`, `useradd --uid 10001`, `USER tunnel`), with every capability dropped (`x-service`, `deploy/compose.yaml:25`).
2. `deploy/compose.yaml:753-757`: it binds `${H4_TUNNEL_DIR}` read-only at `/run/tunnel-client`, so the container sees his folder with his uid and mode 0700.
3. `deploy/tunnel/ssh_config:12` and `:14`: ssh reads `UserKnownHostsFile /run/tunnel-client/known_hosts` and `IdentityFile /run/tunnel-client/id_ed25519`, inside that bind.
4. `deploy/tunnel/entrypoint.sh:111` runs `/usr/bin/ssh -F "$config"` as that same user.

So ssh, as 10001, can't search a 0700 folder owned by his uid: it opens no `known_hosts`, has no key to check the tunnel end's against, and with `StrictHostKeyChecking yes` and `BatchMode yes` (`ssh_config:15`, `:18`) stops at "Host key verification failed". It never gets as far as the key. The fault is P22 working as meant against a container user that isn't him. His ACL gave 10001 the read that the modes deny, and it is gone. No test caught it: the container checks (`deploy/tunnel/test_tunnel.py`, the `tunnel` fixture) `docker cp` the keys into a volume as files owned by 10001 (`tar_of`, "owned by the image's user"), which isn't how the laptop's folder is.

## The options

| | Option | P22 | What it costs | Verdict |
|---|---|---|---|---|
| A | The service starts as root with only `DAC_OVERRIDE`, `SETUID`, `SETGID` added; the entrypoint, as root, opens the two files from the read-only bind and hands their bytes to a `tunnel` process (setpriv, uid and gid 10001, no supplementary group), which writes them 0600 to its own 0700 tmpfs at `/run/tunnel-client`; then it `exec`s itself through setpriv as 10001, so ssh and everything after it run unprivileged with no capability | holds: the folder isn't touched; the bind is read-only, and root in the container has neither `CHOWN` nor `FOWNER`, so it couldn't change the folder's owner or mode if it tried | three capabilities, for the copy's few milliseconds; the compose policy already allows all three (`tools/gates/compose_policy.py`, `CAP_ADD_ALLOWED`), so no human-only path changes | **chosen** |
| B | The service runs as his uid (`user: "${H4_UID}:${H4_GID}"`) | holds | ssh refuses a uid with no passwd entry ("No user exists for uid"), and the image can't know his uid at build, so this needs a passwd entry written at run (a writable `/etc/passwd`, or nss_wrapper) on a read-only root; a new env key, in every env file, P4 and the env tests; and the tmpfs's owner would follow an env value | no |
| C | His ACL back, written by `make tunnel-keys` | breaks it: an ACL's mask shows as the group bits, which P22's `st_mode & 0o077` refuses | — | no (his removal stands) |
| D | `make tunnel-keys` writes a second copy owned by 10001 | the copy's folder isn't his | chown to another uid needs root on his laptop | no |
| E | Compose `secrets:` | — | the compose policy refuses file-backed secrets ("mount host files outside the bind roots") | no |

**Why A.** It is the order's first suggestion, and its root is the smallest that reads the files: root only for the copy, with no capability that could change the folder (`CHOWN`, `FOWNER` aren't added), and the drop is `setpriv`'s, so the kernel clears every capability when the last root uid goes. The bytes are written by the `tunnel` user itself, through a redirection the root shell opens, so root writes nothing and needs no `CHOWN`. ssh's own files (`ssh_config`, `ssh_config_admin`) don't change, nor do their tests: ssh still reads `/run/tunnel-client/`, which is now its own tmpfs. The tunnel end's `server` runs as 10001 as before, and the entrypoint as 10001 does what it did (the container checks' path), so nothing on the tunnel end changes. The admin-only stack (`scripts/operator.py`'s `docker compose run … tunnel admin`, `scripts/test_operator_shared.py:241`) is the same service, so it takes the same copy.

**What "the tunnel never runs as root after the copy" rests on.** The root path of the entrypoint does three things: it checks the two files are there, copies them, and `exec`s `setpriv --reuid=10001 --regid=10001 --clear-groups --inh-caps=-all -- /usr/local/bin/h4-tunnel <mode>`. Nothing else runs as root: the copy's writer is already 10001, and `client`, `admin`, `server`, and `connected` refuse to start as root (exit 77), so a root that reached them by some other path stops. `no-new-privileges` stays on, so nothing after the drop can gain a capability back. The Dockerfile checks at build that `/usr/bin/setpriv` is there (util-linux, in the pinned Ubuntu base).
