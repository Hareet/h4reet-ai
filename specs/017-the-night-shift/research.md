## R-01: nono's version and how it installs

- **Decision**: pin **v0.81.0**, the Linux x86_64 tarball `nono-v0.81.0-x86_64-unknown-linux-gnu.tar.gz`, a single static binary, installed by copying the binary to `~/.local/bin/nono` after its SHA-256 matches the pin. The pin's checksum is the one the probe prints and the Author confirms; it goes into `.devcontainer/toolchain.vars` as `NONO_VERSION` and `NONO_SHA256`, beside the other pins.
- **Rationale**:
  - v0.81.0 was published 2026-10-29 and marked "Latest" and immutable (github.com/nolabs-ai/nono/releases/tag/v0.81.0). It is 14 days old on 2026-11-12, so it meets the two-week rule by the time the Author runs the probe.
  - It fixes three advisories (GHSA-wh99-5qx8-cgh4, GHSA-p39g-3xw6-83jx, GHSA-p398-cgqf-c48x), and "detect[s] Landlock ABI up to V9, keep[s] enforcement at V6" (#2217).
  - A copied binary is the smallest install: no package manager, no install script piped into a shell (the design page's step 3), and `--undo` removes one file.
- **Known issues at v0.81.0**:
  - #2263: `extends` needs a fully qualified pack name (`nolabs-ai/claude`, not `claude`). The profiles don't extend anything (R-03), so this doesn't bite.
  - #2247 (0.80.0 and 0.81.0): a profile with `command_policies` silently loses `dangerous_commands` enforcement. The hooks and the bash gate keep their own dangerous-command rules, so nothing here relies on nono's list; a red-team row records the gap.
- **Alternatives**: v0.80.0 (2026-10-13), comfortably old but without the three fixes; the `.deb` (needs `sudo`, and touches the package database `--undo` would have to clean); `brew`, AUR, Nix (none installed here).
- **Unconfirmed**: the checksum file's name (`SHA256SUMS` or `SHA256SUMS.txt`), and whether the tarball carries a signature or a GitHub attestation. The probe prints the release's asset list with GitHub's own per-asset digest, and any checksum file it finds, beside its own SHA-256 of the download.

## R-02: nono's commands

From nono.sh/docs/cli/usage/flags and the feature pages:

- `nono run [--profile P] [--allow D] [--read D] [--write D] [--allow-file F] [--read-file F] [--rollback|--no-rollback] [--env-credential a,b] [--dry-run] -- cmd`. Supervised execution is the default; `--supervised` is gone.
- `nono profile init <name> --extends <base> [--full] [--output <path>] [--force]`; `nono profile show <name> --json [--raw]`; `nono profile validate <file>`; `nono profile diff`; `nono profile schema`; `nono profile guide`.
- `nono pull nolabs-ai/claude` fetches the Claude Code pack (it replaced the `claude-code` built-in at v0.43).
- `nono audit list|show <id>|verify <id>`; `nono rollback list|show <id> --diff|restore <id>|verify <id>|cleanup`.
- `nono why --path P --op read|write --profile X [--json]` explains a refusal: `{"status":"denied","reason":"not_in_allowed_paths",…}`. `nono learn -- cmd` traces what a command touches.
- `nono setup --check-only` prints, on WSL2, the feature matrix and the Landlock ABI.

The rehearsal uses `run`, `audit verify`, `rollback list`, and `why`; the install uses `profile validate`.

## R-03: profiles, and why each is written out whole

- **Decision**: each role's profile is a complete JSON file with no `extends`, generated by one script from shared fragments (`deploy/night-shift/profiles/build.py`), committed, and checked by a test that the committed files are what the script makes. A second test proves each profile is a subset of its parent, grant by grant, after nono's own path expansion rules.
- **Rationale**:
  - nono's inheritance appends: "Scalar fields (like workdir) override the base, while arrays (like filesystem.allow) append and deduplicate" (nono.sh/docs/cli/features/profiles-groups). A child can't drop a parent's grant (#2269: a child could not drop the pack's keychain grant). So `extends` from the supervisor would give every worker the supervisor's grants, the opposite of "each narrower than its parent".
  - The Claude Code pack grants read and write on `~/.claude`, `~/.claude.json`, and Claude's Linux credential store, and the `claude-code` network profile (groups `llm_apis`, `package_registries`, `github`, `sigstore`, `documentation`) (nono.sh/docs/cli/clients/claude). That's wider than any role here needs. The probe's `profile init --full` output shows the pack's expanded grants; the fragments keep what Claude Code needs to start and drop the rest.
- **Denies**: on Linux, nono refuses to start a profile whose deny sits inside an allowed directory: "Landlock deny-overlap is not enforceable on Linux … Remove the broad allow path, remove the deny path, or restructure permissions" (#2296). So the profiles never grant a broad parent (`$HOME`, the main checkout, `.git`, `/srv/studio`). They grant the subpaths a role needs and list the never-readable paths as denies, which makes nono refuse to start if a later edit ever adds an allow above one. That turns a widening mistake into a refusal.
- **Path variables**: `$HOME`, `~`, `$WORKDIR`, `$TMPDIR`, `$UID`, and the `XDG_*` folders expand; arbitrary environment variables don't. So per-task paths (a worker's worktree) come from `$WORKDIR` (nono's working directory) and `$TMPDIR`, which the runner sets per worker.
- **Format**: JSONC is accepted; the files are plain JSON so Python's standard library reads them in tests.
- **Unconfirmed**: the exact key names for denies and files in the current schema (older docs show `policy.add_deny_access`). The probe prints `nono profile schema` for v0.81.0, and `build.py` is written against that.

## R-04: command policies

- **Shape** (nono.sh/docs/cli/features/tool-sandbox; #2044, #2164, #2247): `command_policies.commands.<name>` with `executable` (a pinned path), `sandbox` (`fs_read`, `fs_write`, `fs_read_file`, `fs_write_file`, `tcp_connect_ports`, `tcp_bind_ports`, `unix_socket_bind`), `from` (which callers may run it), `can_use`, and per-argument entries `{"args":[…],"action":…,"sandbox":…}`. "The supervisor launches each tool into a fresh command sandbox … from a minimal runtime baseline", outside the session's own sandbox. So a command can hold grants the session doesn't.
- **Decision**: command policies for `terraform` (validate, with the provider mirror read and no credential), `docker` (port 2376, the relay's TLS folder), `make` with the `check` argument (its own temp folder), and `blender` (the GPU's paths, no TCP port). ComfyUI is not a command; its port is a session grant of the studio profile (R-07).
- **Caveats**: setting up policies took 76 s in one report (#1317); wrapper and shebang commands can be refused (#1724, #2164), and `make`, `terraform`, and `docker` are real binaries, but `tools/gates/gate` is a Python script with a shebang; no built-in profile has a non-empty `commands` map (#1866). The rehearsal runs each policy once.

## R-05: credentials on WSL2, and the Claude sign-in

- **Decision**: no proxy. Each worker gets its Claude token as nono's environment credential (`--env-credential`, from nono's keystore or a `file://` source outside the repository). The Author makes the token once with `claude setup-token`. The settings patch adds `CLAUDE_CODE_OAUTH_TOKEN` to the sandbox's denied environment variables, so commands the session runs don't see it.
- **Rationale**:
  - nono's WSL2 page: proxy mode and the credential proxy are "blocked by default" because "the child could bypass the proxy". The opt-in, `"security": {"wsl2_proxy_policy": "insecure_proxy"}`, prints "WARNING: WSL2 insecure proxy mode". `--env-credential` works (nono.sh/docs/cli/internals/wsl2-feature-matrix).
  - Phantom-token injection of `CLAUDE_CODE_OAUTH_TOKEN` through a custom route is possible elsewhere (#2269), but needs the proxy.
  - A separate token means the night shift can be signed out without signing the Author out: `claude setup-token` tokens are revocable on their own.
- **Alternatives**: the insecure proxy (names a weaker mode, and the agent's other traffic could leave by a direct path); sharing the Author's `~/.claude` (every worker could write his settings and hooks, which his own sessions then run outside any sandbox).
- **Each role's Claude folder**: `CLAUDE_CONFIG_DIR` set per role to `~/.local/share/h4reet-ai/night-shift/claude/<role>/`, holding only that role's settings layer and history; the Author's `~/.claude` is neither read nor written by any profile.

## R-06: the plan, under decision 1

- **Decision**: the ops worker writes a plan request (root, commit SHA) to its outbox. The runner, outside every sandbox, makes a fresh detached worktree at that commit (`infra_plan.py` checks `infra/` against `HEAD`, so it needs a checkout, not an export). It asks AWS for short-lived credentials for the plan-only role (`aws configure export-credentials --profile h4reet-plan`, from the Author's live SSO session). Then it runs that commit's `scripts/infra/infra_plan.py` inside the `plan` profile, with those credentials as nono's environment credential (`env://`). The branch's code runs only inside nono; the runner itself runs only `git`, `aws`, and `nono`. The redacted block goes back to the worker's inbox; the saved plan stays in `~/.config/h4reet-ai/infra/plans/`, where `make infra-verify` reads it for the Author's apply as today.
- **Rationale**:
  - No per-command `aws_auth` (#1987), and the proxy is off on WSL2 (R-05), so the brief's "`aws_auth` on a plan-only profile" can't hold the credentials outside the plan's process. The next best is credentials that exist only in the plan's process, last an hour, and can only read.
  - `endpoint_policy` matches methods and paths, not AWS actions (#2274), and most AWS read calls are `POST` query calls. So the IAM role is the boundary, as it would have been anyway.
  - Today the Author runs the branch's own `infra_plan.py` in his terminal with his administrator session (the runbook's step 10c). The night shift's plan runs the same code with a read-only role inside a sandbox, which is narrower than today on every axis.
- **The role** (`h4-agent-plan`, his patch to `infra/account/iam.tf`):
  - its trust: the Author's Identity Center permission set role, through `sts:AssumeRole`, with a one-hour session;
  - its permissions: AWS's managed `ReadOnlyAccess`, minus `ssm:GetParameter*` with decryption and `secretsmanager:GetSecretValue`, plus `s3:PutObject` and `s3:DeleteObject` on `<state bucket>/*.tflock` only, so plans lock as his apply does (Clarifications);
  - its tags: project, environment, component.
- **Unconfirmed**: whether `ReadOnlyAccess` covers every data source the roots read (budgets, Identity Center); the first plan under the role says, and a refusal names the action.

## R-07: the network on WSL2

- **Decision**: each profile opens only the TCP ports its role needs: 443 for all; 2376 for the roles that run containers (implementer, red-teamer, ops, the gate runner); ComfyUI's port for the studio; 2376 and the npm and PyPI mirrors' 443 for `make check`. The hosts are held by the layer R-08 proves.
- **Rationale**: "Landlock rules match TCP ports, not IP addresses … Use the domain proxy, not a raw port grant, when destination-host enforcement matters" (nono.sh/docs/cli/features/networking), and the domain proxy is off on WSL2. The kernel is 6.18 (Landlock ABI 7 per #2080; nono enforces up to V6, so V4's TCP port rules apply).
- **Gap, named**: a session under nono alone can reach any host on 443. Claude Code's sandbox holds the host list for every Bash command where it runs (R-08); the permissions deny `WebFetch`; the bash gate refuses `curl`, `wget`, `nc`, `ssh`. A red-team gap row records the kernel layer's port-only limit.

## R-08: the nesting, and the outer mount namespace

- **Finding**: the kernel's Landlock documentation says a thread "sandboxed with filesystem restrictions cannot modify filesystem topology, whether via mount(2) or pivot_root(2)". Claude Code's sandbox on Linux is bubblewrap, which mounts. So Claude Code's sandbox is unlikely to start inside nono's. No nono document or issue covers it; third-party setups put bubblewrap outside nono (GRBurst/ai-sandbox).
- **Also**: Unix sockets are unmediated under nono on WSL2. Mediation needs `"linux": {"af_unix_mediation": "pathname"}`, done by seccomp user notification, which returns `EBUSY` on WSL2 (microsoft/WSL#9548). So under nono alone, a session could connect to `/var/run/docker.sock`, which is root on the host.
- **Decision** (FR-037, FR-038):
  1. The probe tries it on the Author's machine (§R-14): bubblewrap inside nono, the Docker socket inside nono, and the fallback below.
  2. **Nested, if it starts**: Claude Code's sandbox runs inside nono's, as today plus nono.
  3. **The fallback, if it doesn't**: the runner starts each session as `unshare --user --map-current-user --mount` → bind `/dev/null` over the Docker socket and an empty `tmpfs` over each never-readable folder → `nono run …` → `claude`, with Claude Code's own sandbox off in the role's settings layer and every hook on. The mounts happen before nono's Landlock domain exists, so the order is allowed. This is the "bubblewrap outside nono" shape, done with `unshare` and `mount` from util-linux.
- **What each layering loses**: the fallback loses Claude Code's per-command host list (R-07's gap) and its per-command read masks, which the outer namespace and nono's own grants replace. The nested layering, if it works, loses nothing.

## R-09: the gate, under decision 2

- **Finding**: the gate (`tools/gates/gate`) refuses to start "unless HEAD is refs/heads/main" in its checkout, with a clean tree. Its container phase runs on the host's engine (`HOST_ENGINE = "unix:///var/run/docker.sock"`), and its image step uses the Author's engine certificate in `~/.config/h4reet-ai/agents-engine/docker`. Its `--prove` runs `deploy/agents-engine/engine.sh prove`. It never merges; it prints the merge line.
- **Decision**:
  - **The gate checkout**: a linked worktree of main at `~/h4reet-ai/gate`, made by the install script (`git worktree add ~/h4reet-ai/gate main`, from the Author's terminal, where his git is outside the bash gate). No profile writes it. His own checkout stays parked off main, so agents keep committing. He merges from the gate checkout.
  - **The gate runner**: a worker that asks the runner for a gate (branch, SHA). The runner takes the gate lock and runs `tools/gates/gate <sha>` from the gate checkout under the `gate` profile, whose grants are the host's Docker socket (outside the outer namespace's mask), the engine certificate's folder (read), the gate checkout (read), its temp folder, and gitleaks. The log goes to the worker's inbox and the decision page.
  - **No `--prove`** (Questions, Q7): stage E stays PENDING for the Author.
- **Why it's acceptable**: the gate is main's reviewed code, built to run an untrusted branch as data in `--network none` containers with every capability dropped. The agent chooses only the SHA. The host socket is granted to that one command, which the agent can't edit (the gate checkout is read-only to every profile, and the gate refuses an unclean tree).

## R-10: the runner, the queue, and the locks

- **Decision**: the runner is one Python file (`deploy/night-shift/runner/night.py`, standard library only, run as `python3 -I -B`), installed by the Author's script from the reviewed commit into `~/.local/share/h4reet-ai/night-shift/`. It is the only process outside every sandbox. It:
  - reads the queue (`queue.json`, contracts/queue.md), which the supervisor writes in its own worktree, and validates each task's role, locks, and dependencies;
  - makes each task's worktree under `~/h4reet-ai/night/<task>` and its branch, outside the sandbox;
  - holds the locks as `flock(2)` on files in `~/.local/state/h4reet-ai/night-shift/locks/`, which no profile can write;
  - starts at most ten workers (`claude -p … --output-format stream-json`), each under its role's profile, and watches their streams;
  - runs plan and gate requests (R-06, R-09);
  - on a usage-limit message, reads its reset time, stops the workers, sleeps once until then, and resumes from the save points; it never polls;
  - stops a worker whose worktree is clean and whose stream has been silent for the idle limit (15 minutes, a setting);
  - writes nothing to the repository but the worktrees it makes.
- **Rationale**: a worker's profile can't be narrower than its parent's if the parent is the supervisor's Claude process (nono nests inside the outer domain, and a nested nono's supervisor can't hold anything the outer one can't reach, credentials included). Starting every session from one process outside the sandboxes keeps each under its own top-level nono, with its own audit log and rollback. That process is deterministic code the Author installs from a reviewed commit, as `engine.sh` is.
- **Save points**: the worker's role prompt commits before each step (`wip(<task>): <step>`); the runner records any session that ends with uncommitted changes, never commits for it.

## R-11: the studio line

- **Decision**:
  - The schemas live in the repository (`contracts/` of this spec, and `scripts/studio/line.py`, which validates them with the standard library).
  - The intake's own checks are main's `tools/gates/arrival_check.py`, run on a copy of the candidate in a scratch repository, plus the brief's limits (triangles, bones and their names, clips, texture size, file size) from the GLB's JSON chunk.
  - The weights and nodes list is `assets/policy/studio-tools.json`, a new human-only file (his patch). Each entry names its kind (weight or node), name, version, licence ID from `licenses.json`, and `outputs_ship` (true or false). Qwen-Image-2.1 and FLUX [dev] are listed with `outputs_ship: false`; they stay "evaluate-only" (intent 003).
  - The folders `/srv/studio/briefs/` (repo roles write, the studio reads) and `/srv/studio/handoff/` (the studio writes, repo roles read) are made by the install script, owned by the Author.
- **ComfyUI**: the studio agent queues a workflow's JSON with `POST /prompt`, waits on `GET /history/<id>`, and fetches with `GET /view`. It reads `/srv/studio/workflows` for the workflow files. It can't reach ComfyUI's install folder, its `custom_nodes`, or its models, and can't call ComfyUI-Manager's install routes, which the studio's settings layer refuses by permission rule and a hook.
- **Blender**: `blender -b --python <script>` under its command policy: the GPU's paths (`/dev/dxg`, `/usr/lib/wsl/lib`, read), Blender's own folder (read), the studio's working folder and the handoff folder (write), no TCP port. `--allow-gpu` is listed as working on WSL2 ("WSL2 uses /dev/dxg … CUDA and ollama inference verified"); whether it covers `/usr/lib/wsl/lib` is unconfirmed, so the policy names both paths.

## R-12: how the Author's script stays exactly what he read

- **Decision**: the install script is a file in the reviewed commit, run as `bash <(git -C ~/h4reet-ai/h4reet-ai show "$sha:deploy/night-shift/install.sh") "$sha"`, after a guard that `git rev-parse` of the branch is that SHA. It reads every file it installs with `git show "$sha:<path>"`, uses `/usr/bin/python3 -I -B` for its one JSON step (placeholder filling), and runs `git` with `GIT_NO_REPLACE_OBJECTS=1`, `GIT_CONFIG_NOSYSTEM=1`, and `-c core.hooksPath=/dev/null`, so no hook, replace ref, or project config runs. It runs nothing from a working tree.
- **Its machine facts**: `~/.config/h4reet-ai/night-shift.env`, which the Author writes from the probe's summary (the paths, ports, and versions; the AWS profile name for the plan role, later). Never in the repository.

## R-14: the probe

- **Decision**: one script, `deploy/night-shift/probe.sh`, in `.claude/agents/ops.md`'s pattern. It writes only inside `mktemp -d /tmp/h4-probe.XXXXXX`, and points every nono folder there (`XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`). It prints to the terminal and keeps the same text in `report.txt` in that folder, so this session can read it by path once the Author has read it.
- **What it adds to the brief's list**: one short block that runs the downloaded nono from the temp folder, four times, with all of nono's state there:
  - bubblewrap inside nono (the nesting, R-08);
  - a connection to the Docker socket inside nono (sends nothing);
  - a read of `~/.aws` inside nono, reported by exit code only;
  - the outer namespace's mask, then the same connection.

  This answers the plan's largest unknown before anything is built on it. It installs nothing; the block is marked so the Author can delete it before running if he'd rather not.
