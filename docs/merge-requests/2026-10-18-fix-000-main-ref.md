## What changed and why

git resolves a bare name through six rules in order (refs.c's `ref_rev_parse_rules`): `main` itself, at the top of `.git`; `refs/main`; `refs/tags/main`; `refs/heads/main`; `refs/remotes/main`; `refs/remotes/main/HEAD`. I checked them with git 2.43.0, this host's, in a throwaway repository: with `refs/tags/main`, `refs/main`, or a file `.git/main` at an older commit, `git rev-parse main` printed that commit, with only a warning that the name is ambiguous; with `refs/remotes/main` or `refs/remotes/main/HEAD` it printed the branch's, with the same warning. So the request's list, `refs/main` then `refs/tags/main`, misses the first rule: a file `.git/main` answers first, `for-each-ref` never lists it, and git 2.43's `update-ref main <commit>` writes one, even from a linked worktree, since it lands in the shared `.git`.

1. **The gate reads main only as `refs/heads/main`, and stops while another ref a bare `main` names exists** (`tools/gates/gate`, in the patch).
   - Three reads named main bare: `git cat-file blob main:GNUmakefile` in `makefiles()`, the step that decides whether the container phase's make may read the export's `GNUmakefile`; `git merge-base main SHA` in `run_gate()`, the base of the gitleaks range, of the changed paths stage E and the behavioral step read, and of the eval-history step's diff; and `git merge-base --is-ancestor main SHA` in `finish()`, the note under the merge command. Each now names `MAIN`, `refs/heads/main`, through the gate's `git()`, which already sets `GIT_NO_REPLACE_OBJECTS=1` on every call. The docstring's gitleaks line says so too.
   - `main_shadows()` lists the five other names that are refs: whatever `git for-each-ref --format=%(refname)` lists, loose or packed (a symbolic ref too), and a file or link at each name's `--git-path`, which finds `.git/main` and a loose ref git can't read. `export()` stops on any, right after its `refs/replace` stop and in the same way: `export` FAILs, nothing else runs, exit 1. The message names each ref, `.git/main` with its path, and how to remove it: `git update-ref -d --no-deref <ref>`, or `rm` for `.git/main`, which git 2.43 won't delete by that name ("refusing to update ref with bad name 'main'").
   - Why stop, when the gate no longer reads them: your own `git diff main...<branch>`, `git log main`, or `git show main:<path>` before a merge would read the tag. The gate is the one place you look before merging, so it says so.
   - And again at the end (the review's item 2): the container phase runs for minutes, so `finish()` runs the same check before the summary. If a ref has appeared since the export, a `main-refs` step fails with the same message, the summary counts it, and no merge command is printed. With none, there is no `main-refs` line at all, so a clean run's output is unchanged. The message lives in `shadow_problem()`, which both use.
   - The paths come relative to the repository: with `--path-format=absolute`, git resolves each path and fails when `refs/remotes/main` is a file, since `refs/remotes/main/HEAD` can't be under it. The first GREEN run caught that.
   - `refs/remotes/<remote>/main`, a remote-tracking branch, never answers for a bare `main` (it is `<remote>/main`), so it doesn't stop the gate, and neither do `refs/tags/main-v1`, `refs/tags/v1/main`, or `refs/heads/topic/main`.
2. **The git hook refuses creating or changing them inside Claude Code** (`.claude/git-hooks/reference-transaction`, in the patch). After its check on `refs/heads/main`, unchanged, a `case` on each ref name refuses `main`, `refs/main`, `refs/tags/main`, `refs/remotes/main`, `refs/remotes/main/HEAD`, and any other ref outside `refs/heads` whose last component is `main` (`refs/tags/v1/main`, `refs/notes/main`, and git's `main-worktree/main` and `worktrees/<id>/main`), but a remote-tracking branch, `refs/remotes/<remote>/main`. That exception is a departure from the request's "any ref outside refs/heads whose last component is `main`": after publication an agent's `git fetch` updates `refs/remotes/origin/main`, and the hook would refuse that update, so the fetch would fail. A deletion (a new value of all zeros) goes through, so a session can remove one it finds. Your terminal, without `CLAUDECODE`, is unaffected, as before.
   - What the hook can't see: git 2.43 runs no reference-transaction hook for `git symbolic-ref`, which writes `refs/tags/main` or `.git/main` straight to disk; nor for a file written directly. `bash-gate.sh` refuses the `symbolic-ref` spellings and `.git/main` and `.git/refs/` writes, and the gate stops on all of them.
3. **`bash-gate.sh` refuses the spellings it can read** (`.claude/hooks/bash-gate.sh`, in the patch):
   - `git tag` whose tag name is `main`: after git's global options (`git -C`, `-c`), quotes around the subcommand, and the options that create a tag, `-a`, `-f`, `-s`, `-e`, and `-m`, `-F`, `-u` with their values, quoted or attached (`-fam x`, `--message=x`). Never after `-l`, `-d`, `-v`, `--contains`, `--merged`, or `--points-at`, which read or delete; nor when main is a message, a commit, or part of a longer name (`git tag -m main v1`, `git tag v1 main`, `git tag main-v1`, `git tag maintenance`).
   - `git update-ref`, `git symbolic-ref`, or a fetch refspec's destination naming `refs/main`, `refs/tags/main`, `refs/remotes/main`, or `refs/remotes/main/HEAD`. (`main` itself was refused already, by the "moving main" and "pointing HEAD at main" rules.)
   - A fetch destination as git reads it (the review's item 1, which found three spellings that got past the first version): `tags/main` and `remotes/main`, since git puts `refs/` before a destination starting `tags/` or `remotes/`; a glob at `refs/*`, `refs/remotes/*`, or `remotes/*`, which lands a branch `feature/main` at `refs/main` or `refs/remotes/main`; and the refspec in a remote's fetch setting, `-c remote.<name>.fetch=…` before `fetch` (or `git config`, which the remote rule refused already). I ran the three in a throwaway repository: without the hook, each wrote `refs/tags/main` or `refs/main` (the glob wrote both, from branches `feature/main` and `feature/tags/main`); with it, each was refused and left nothing. The usual fetches stay allowed: `+refs/heads/*:refs/remotes/origin/*`, `refs/tags/*:refs/tags/*`, `--tags`, and a destination that only contains `tags/main` or extends it.
   - A write to `.git/main`, added to the "writing git internals" rule, which already covered `.git/refs/` and `.git/packed-refs`.
   - Both new rules read the command three ways, as the closing patch's rules do (as written, with backslash-newlines joined, and with comments ended), and quotes, backslashes, and `$` inside a name don't hide it (`ma''in`, `\main`). The spellings CLAUDE.md asks for are rows: `git -C .`, `git -c`, `bash -c '…'`, a subshell, quoting, and a chained command.

The git hook refuses all but the `.git` write; the gate stops on all six.
