## What changed and why

User Story 6's counts, the half of it that needs no model call: the room's usage events leave the browser as beacons carrying a kind and an ID alone, the gateway turns each into one increment of a counter, and the dashboard's "Room" row reads them. Nothing is stored but the count.

1. **The beacon (T060; contracts/room-events.md §1).** `apps/web/src/events.ts`, `beaconEvents(navigator)`: the `EventSink` the page now hands `startRoom`, in place of Phase 4's default, which sent nothing.
   - One `navigator.sendBeacon("/api/room/events", body)` per event. The body is built from the event's `kind` and `id` alone, so it is `{"kind":…}` or `{"kind":…,"id":…}` whatever else a caller's object holds.
   - The body is a string, so the browser sends it as `text/plain;charset=UTF-8`: a beacon needs no preflight for that type, and the gateway takes it beside JSON (§3).
   - An event the gateway would refuse is never sent: a kind the room doesn't know, or an ID-taking kind without its ID. An ID on a kind that takes none is dropped from the body.
   - A beacon the browser refuses (`false`) or that throws is dropped: no retry, no queue, no storage. Without `sendBeacon`, nothing is sent, and never another way.
   - The room's own default sink, and the screen tests', still send nothing; the tests collect events in memory.
2. **The gateway's route (T059; contracts/room-events.md §3).** `services/gateway/src/routes/room-events.ts`, `POST /room/events` on the api listener, which edge's x005 already forwards `/api/room/events` to, with its rate limit and 512-byte cap (Phase 1).
   - **The order is the contract's:** a `Content-Type` of `application/json` or `text/plain` (parameters allowed), else 415, counted `content_type`; a JSON object of `kind` and an optional `id`, both strings, else 400 `shape`; a `kind` in the list, else 400 `kind`; an `id` exactly when the kind takes one, else 400 `shape`; and the `id` in its kind's list (`objects` for `object_selected`, `items` for `item_selected`), else 400 `id`.
   - **On success:** `h4.room.events{kind, id}` goes up by one, with `id="-"` for a kind that takes none, and the answer is 204 with no body.
   - **The refusals' bodies** are the listener's own shapes: 415 `{"error":"unsupported_media_type","request_id":…}`, and 400 `{"error":"invalid_request","field":"body"|"kind"|"id","detail":…,"request_id":…}`, with fixed details that never echo the body.
   - **Its own scope.** The route sits in a Fastify plugin scope whose only body parser reads any type as text for the route to check, so the listener's other routes still refuse anything but JSON (gateway-http.md §1). A refusal Fastify makes before the handler (a `Content-Type` that doesn't parse, a body over the listener's 16 KB) is answered by the listener's error handler as on every route, and counted by the scope's `onError` hook.
   - **What it never does:** write a log record, put the body in a span, run a store statement, write a ledger, reservation, or audit row, touch the journal, call a model, or admit anything to the meter. It isn't under `/hello`, so the per-client cap, routing, and the meter never see it, and it doesn't count in `h4.gateway.requests`. It answers while the store is down.
3. **The event list (T059).** `services/gateway/src/config/room-events.ts` reads `config/room-events.yaml`, the committed file Phase 4's `build/manifest.ts` writes, from the same mounted `config/` as the gateway's four files. `server.ts` reads it at start, YAML and zod only, before telemetry starts.
   - It is checked as strictly as the four: one YAML document, no duplicate key, `schema: 1`, no other key, kinds and IDs matching the room's own patterns, no duplicates, and at most 32 kinds, 64 objects, and 256 items, so the counter's series stay bounded.
   - **Unlike the four, it never stops the gateway.** A missing or invalid file logs `room_events.unavailable` (warn) with `reason` (`missing`, `invalid`) and `path` (where the file is invalid, such as `objects[0]`; never a value from it). Every event that passes the content type and the shape is then 400 `id`.
4. **Telemetry (FR-055; spec 000's telemetry.md).**
   - **§4.1:** `h4.room.events` (counter, `{event}`, `kind` and `id`; `h4_room_events_total`) and `h4.room.events.refused` (counter, `{event}`, `reason`; `h4_room_events_refused_total`). The attribute keys are the room contract's bare `kind`, `id`, and `reason`, not spec 000's `h4.` prefix, so the Prometheus labels are the ones quickstart §6 reads (plan.md §6, "As built").
   - **§5.2:** `room_events.unavailable`.
   - **§3.2:** the route's server span, with nothing under it: no routing span, no model call, and `h4.outcome` `ok` for its 204 and `invalid` for its 400 and 415.
5. **The "Room" row (T061; telemetry.md §7.8; FR-056).** Six panels in `deploy/grafana/dashboards/h4-runtime.json`, under a row titled "Room", above the development-time row:

   | Panel | What it reads |

## Backlog

- **Per day is the last 24 hours, not a calendar day.** A past day reads by ending the range at its midnight (UTC). A per-day series that doesn't depend on the range needs a Prometheus recording rule, or a daily step, whose alignment hides today's counts (above).
- **`increase()` extrapolates,** so a count can read 1.1; the bars and the stat show whole numbers.
- **Every event is a Langfuse trace.** That's plan §9's server span, and it carries no visitor data, but once spec 001 opens the site, the room's events could outnumber every other trace. Sampling the route's spans, or filtering them in the collector as the health probes are, is a decision for spec 001's plan.
- **The kinds that take an ID** are known in two places, the room's `src/events.ts` and the gateway's `routes/room-events.ts`; a new ID-taking kind changes both, and `config/room-events.yaml` would need to say which list its IDs come from.
- **A visit that keeps the resume and opens it later** counts twice in the 2D share's denominator, so the share reads low; the contract chose this stand-in because no visit is counted.
- **Nothing ran on a stack.** The edge's forwarding, the 60 s budget, the labels in Prometheus, and the empty Loki query are T063's, yours.
