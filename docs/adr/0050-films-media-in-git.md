# ADR 0050: The films' renders in plain git, in each film's `media/` folder: MP4 and GIF only, capped, with no place and no XMP (rule A11)

Status: proposed, 2026-11-11, for the Author to accept · Intent: 015 (the spec stage waived for the films, as the intent's open questions record) · Extends [ADR 0031](0031-assets-in-plain-git.md)'s fixed roots by one folder outside the asset tree; changes no decision of [ADR 0030](0030-media-license-and-ai-mark.md) or [ADR 0032](0032-pre-publication-cleanup-for-assets.md) · Number: the next free one across the branches (0047 is spec 001's shared account, on `main`; 0048 and 0049 are `feat/001-w1`'s)

## Context

Intent 015 makes seven explainer films for the resume's claims, "made with the huashu-motion skill as editable code (HTML and GSAP) and rendered to MP4". Its data-flow impact records where they live, in the Author's words of 2026-11-10: "we'll keep it in films"; "we are going to merge these videos into the main repo, and then push everything up". The intent places them: "The rendered MP4s and one GIF go in `films/<name>/media/` once the arrival check admits them (ADR 0050)." The Author's decision of 2026-11-10 put the renders there, not under `assets/films/`.

Today the arrival check refuses them. Rule A1 refuses "an image, video, or model file outside the asset roots", found by extension or by leading bytes, so a studio file can't hide outside `assets/` and `docs/research/images/`. Under `assets/`, rule A3 admits only PNG, JPEG, WebP, GLB, `records.json`, and `LICENSE.md`. What `films/` holds now passes: each film's `index.html`, `vendor/`, WOFF fonts, and WAV narration were committed with "arrival-check: 0 findings". A WAV (RIFF `WAVE`) and a WOFF are neither an extension nor a signature A1 lists, so they meet only A4's camera-metadata search, which they pass.

Why a GIF beside the MP4: the README's Films section shows one film inline as a GIF (intent 015: "a Films section in the repository's README with one film shown inline as a GIF"), the kill-switch film's, because GitHub's Markdown renders a GIF as an image, and a repository MP4 linked from a README doesn't play there. `films/RESUME-LINKS-PLAN.md` adds that "a GitHub file view may offer the MP4 as a download rather than play it, depending on its size and the browser", which is why the resume links to each film's landing page.

What the films are: code, rendered by headless Chrome and FFmpeg on the Author's machine; every string and number on screen sourced in the film's `materials.md`; "a synthetic voice (Kokoro) reads the session's scripts, which the Author approved, and the Author may record over a locked cut" (intent 015). ADR 0030 doesn't reach them as written. Its media license "covers `assets/` and `docs/research/images/`", and its mark goes in "every published image and model file", where spec 003 defines a published image as "a studio-made image in a document" and an asset as "any file the studio makes that comes into this repository". The films aren't the studio's: no studio pipeline makes them. The voice is a model's, so the AI disclosure matters, and it is already made to people: the README says "The narration is a synthetic voice (Kokoro)", and each landing page "the narration is a synthetic voice". The mark's machine form, an XMP packet, is what this rule keeps out of a render.

The renders as of 2026-11-11, read with `ffprobe` and a box walk: every one of the 27 MP4s under `films/*/out/` carries the same tags and nothing more: `major_brand=isom`, `compatible_brands=isomiso2avc1mp41`, `encoder=Lavf60.16.100` (the `©too` atom), and per track `handler_name` (VideoHandler, SoundHandler), `vendor_id=[0][0][0][0]`, `language=und`, and `encoder=Lavc60.31.102 libx264`. No title, comment, date, or location; no `uuid`, `XMP_`, `©xyz`, or `loci` box. x264's own options string sits in the first frame's SEI, inside `mdat` (`x264 - core 164 ... options: cabac=1 ... threads=34 ...`), with no path; the B rules don't scan media data. The kill-switch GIF holds GIF89a, one `NETSCAPE2.0` loop count, 174 graphic controls and images, no comment, no other application extension, and nothing after its trailer.

## Decision

1. **The root.** `films/<name>/media/`, where `<name>` matches `[a-z0-9-]+` and `films/<name>/` holds the film's `index.html`. It isn't an asset root: no `records.json`, no `LICENSE.md`, no mark, no approval, none of the R, N, L, P, or F rules. A file there must be a plain file: never a link, a submodule, or a subfolder.
2. **The formats.** An MP4, by its name (`.mp4`), an `ftyp` box at byte 4, and an MP4 brand (`isom`, `iso2`, `iso4` to `iso6`, `mp41`, `mp42`, `avc1`); and a GIF, by its name (`.gif`) and `GIF87a` or `GIF89a`. Nothing else: no PNG, no poster frame, no text file, no MOV under another name.
3. **The caps,** per file: an MP4 at most 60 MiB (62,914,560 bytes), a GIF at most 10 MiB (10,485,760 bytes). The MP4 cap stays under GitHub's 100 MB per-file limit. GitHub warns on a push over 50 MB, which the stack film (56.3 MB) will meet.
4. **The metadata,** parsed, never searched. An MP4's boxes are walked down the containers that hold its tracks and their metadata (`moov`, `trak`, `mdia`, `minf`, `stbl`, `edts`, `dinf`, `udta`, `meta`, `ilst`, and the fragment boxes). Refused: a location atom (`©xyz`, `loci`), a `keys` box naming a location, an `XMP_` box, a `uuid` box (XMP's `BE7ACFCB-97A9-42E8-9C71-999491E3AFAC`, or any other, whose contents nothing here can read), a track whose handler isn't `vide`, `soun`, `text`, `sbtl`, or `subt` (a timed-metadata track, where a camera keeps its GPS), a metadata handler other than `mdir` or `mdta`, a top-level box an MP4 doesn't hold, and any byte no box accounts for. A GIF's blocks are walked to its trailer. Refused: an XMP application extension (`XMP DataXMP`), any application extension but the loop count's (`NETSCAPE2.0`, `ANIMEXTS1.0`), an unknown block, and any byte after the trailer. Admitted: the encoder's tags FFmpeg writes (`©too`, `handler_name`, `vendor_id`). The B rules (a prompt or workflow record, a model file's name, a local path) read every `udta`, `meta`, and `hdlr` box and a GIF's comments; rule A4 searches the whole file, as it does every binary file. Media data isn't read, as the B rules' scope already has it.
5. **One rule ID, A11,** in the existing format, `A11 <path>[ @<commit>]: <reason>`. Every mode applies it alike: `--staged`, `--range`, `--history`, and named paths, through the same per-file check. Anywhere else under `films/`, an image or a video meets A1 as it does today.
6. **What to commit:** final cuts only. A film's media folder holds its MP4 and, for the films the README shows, one GIF. The comparison cuts (`films/kill-switch`, `-b`, `-mix`) stay code.

The rule, in the arrival check's docstring:

> - A film's renders (rule A11, ADR 0050): in films/<name>/media/, where films/<name>/ holds the film's index.html, only an MP4 (its name, an ftyp box at byte 4, an MP4 brand) of up to 60 MiB and a GIF (its name, GIF87a or GIF89a) of up to 10 MiB, each a file, never a link or a subfolder; no place and no XMP in either (an MP4's ©xyz or loci atom, a location key, an XMP_ or uuid box, or a timed-metadata track; a GIF's XMP, or any application extension but the loop count's), and no byte its boxes or blocks don't account for. The encoder's own tags (©too, the handler names) pass, and meet the B rules with every udta and meta box and a GIF's comments; the whole file meets A4. No record, no notice, no mark: the films are code, and their renders this code's output. Anywhere else under films/, an image or a video meets A1 as it would anywhere.

The patch, human-only since it changes `tools/gates/`: `docs/merge-requests/2026-11-11-films-media-gate.patch` (the check, its fixtures and tests, and spec 003's `contracts/arrival-check.md`, §2, §3's A11 row, and §5).

## Alternatives considered

- **`assets/films/`:** an asset directory takes only PNG, JPEG, WebP, GLB, `records.json`, and `LICENSE.md` (A3), each format one the check parses completely (research R-02), each file with a record, the media license's notice, and the mark (R, N, M5). A video would need an M rule of its own and a record for a file no studio made, and its blobs would count toward the asset roots' 500 MB history cap (H1). The Author chose `films/`.
- **GitHub user attachments** (a video dragged into an issue or a README edit, served from `github.com/user-attachments/`): they play inline in a README. But they need the repository published, which ADR 0013 keeps local until the Author publishes; they live outside git, so no clone, no local tier, and no gate has them; and the arrival check can't see them.
- **Git LFS:** the clone stays small and a re-cut doesn't grow every clone's history. Against it, ADR 0031's reasons still hold (GitHub meters LFS storage and bandwidth past a free allowance; a clone without LFS holds pointers, not films), and more: the index and the history hold only pointer files, so the pre-commit hook, the gate's range, and `make publish-check`'s history scan would check pointers, not the renders, unless the check learned to read LFS's object store; and ADR 0032's cleanup would have LFS's object store to clean as well as the history. Worth revisiting if the films' blobs in the history pass the asset roots' own 500 MB cap.
- **No GIF, the MP4 alone:** a README would show the film as a link, not a picture.
- **A wider rule** (any `media/` folder, or MOV and WebM too): more than seven films and one GIF need.

## Consequences

- **Repository size.** The seven films' final cuts (rendered 2026-11-12) total 229,001,068 bytes (21.6 to 56.3 MB each: five between 21.6 and 27.9 MB, `lifecycle` 47.5 MB, `stack` 56.3 MB), and the kill-switch GIF 7,038,051 bytes: about 236 MB in every clone. Compressed video doesn't shrink in a pack. The history keeps every version committed, so a re-cut adds its full size for good: commit final cuts only, best once the cuts are locked and the Author has settled intent 015's open question ("Whether the Author records the narration or keeps the synthetic voice"), so the history holds one version of each.
- **No history cap for the films.** H1 counts the asset roots only; A11 caps each file, not the folder's history. The Author holds the history by what the Author commits; the merge-request note of the media commit records the total.
- **The caps' headroom.** All 29 current renders pass A11 but two superseded kill-switch cuts (v2, 67.6 MB; v4, 64.7 MB), neither a final cut. The largest final cut, `stack`, is 56.3 MB, with 6.7 MB of headroom; a longer film at the same bitrate may need a lower CRF or a cap the Author raises in a patch.
- **ADR 0032 still covers what the check can't see.** A11 reads containers, never frames. A frame that shows a secret, a private path, or anything that locates the Author is the intent's constraint ("No secret, token, key, private photo or private path on screen"), checked by the Author's viewing before the media commit. Found before publication, it's ADR 0013's cleanup, as ADR 0032 extends it: the Author rewrites the history; after publication, a withdrawal and an incident note.
- **A studio video can't hide here unchecked.** A1's purpose stands for everything else: an MP4 under `films/` outside a film's own `media/` folder is still refused, and inside one it must be a film folder's, with no place and no XMP. A studio render placed there on purpose would pass the machine; the reviewer and the Author's merge are what stop it.
- **The license and the AI disclosure** (ADR 0030 doesn't reach `films/`, as the Context reads it). The Author decided on 2026-11-12: "MIT." So `films/`, renders included, stays under the MIT license with the code, as the repository already has it: the README's license line is unchanged, and no folder takes a `LICENSE.md` (A11 admits only MP4 and GIF). The synthetic voice stays disclosed to people where it is now, in the README and each landing page; no machine mark goes in a render, since A11 refuses the XMP the mark would need.
- **No data flow.** The renders live in the repository; the site doesn't serve or link them (intent 015). If the site ever serves one from its own origin, or a third-party player, that is new work with its own disclosure row first, as `films/README.md` says.
- **Cost: $0.** No cloud spend; the check's time grows by a box walk and one search per render (the 29 renders under `films/*/out/`, 1,102,437,467 bytes, took 3.8 s by path in an agent session's sandbox).
