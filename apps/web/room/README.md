# The room's data

This folder describes the room as data, so moving, adding, regrouping, retargeting, rewording, or removing a piece changes no source file (spec 004, FR-001 to FR-006). The compositor in `apps/web/build/room/` reads it strictly and composes it into the bundle the 3D room, the 2D room, and the lists draw from. A new kind of behaviour, such as a new stand-in shape, renderer, signal, or look method, is code, made through the lifecycle (FR-005); so are the hand-off and its paper (FR-008).

| File | Holds | Contract |
|---|---|---|
| `catalog/<piece>.yaml` | one piece each, its stem the piece's ID: its size, stylized scale, origin and bounds, anchors, live faces, glows, claims, stand-in, 2D drawing, budget, model, and work order | contracts/room-data-files.md §4 |
| `scene.yaml` | the placements, the switches, the selectables, the hand-off, the live configuration, the survey, and the retired IDs | §5 |
| `topics.yaml` | the topics the selectables open | §6 |
| `ui-words.yaml` | every UI word: the code's closed list, and the `label.<name>` words the scene references | §9 |
| `looks/<look>.yaml` | the looks; `scene.yaml`'s `look` names the chosen one | §10 |
| `fixtures/<fixture>.yaml`, `lookdev.yaml` | samples and the lookdev page's views, for drafts builds and tests only | §11, §12 |

Room text, the words the room draws on a face, sits in `apps/web/content/room/` and is approved by its hash (§7, §8). This README is prose: the compositor never reads it.

## The commands

From the repository's root:

| Command | Does |
|---|---|
| `npm run room:generate -w apps/web` | writes the generated files from the data: `config/room-events.yaml`, `config/room-topics.yaml`, and `docs/studio/`'s work orders and photo guide, removing a work order whose piece is gone. It writes nothing while the data has a finding a lenient build doesn't tolerate. `npm run manifest -w apps/web` is its alias |
| `npm run room:check -w apps/web` | composes in strict mode, prints every finding, and fails on any, or on a generated file that is stale, missing, or orphaned. `make test` holds the same rules |
| `npm run room:report -w apps/web` | prints the room's report: each piece's bytes, triangles, and texture memory against its budget and the caps, the faces' legibility, its Side-wall section (each side-wall selectable the room leaves to the "In the room" list, its wall, and the stages where, in 3D and in 2D), the switches' poses, and the findings. A merge-request note whose branch changes the room's data or models pastes it whole |
| `npm run room:scan -w apps/web` | the source scan: no ID the data defines may stand in the code (FR-007) |
| `npm run room:fit -w apps/web -- <glb> --piece <id>` | the fit check of one model file in the tree against one catalog entry |

Every change ends the same way: run `npm run room:generate -w apps/web`, then `npm run room:check -w apps/web`, and commit the data with the generated files it changed. Nothing under `apps/web/src/`, `apps/web/build/`, or `apps/web/test/` changes.

## The rules every change meets

- **YAML, read strictly.** One document, `version: 1`, UTF-8 with LF line ends, no anchor, alias, merge key, or tag, and no key the schema doesn't define (RD). Prettier formats every YAML file here (`make fmt`).
- **IDs.** `^[a-z][a-z0-9-]{1,40}$`, unique within their namespace (pieces, placements, selectables, topics), never a word of the closed vocabulary in `apps/web/src/room/compose/vocabulary.ts`, and never an ID `retired[]` lists for that namespace (RI). The prefix `fx-` belongs to the tests' fixtures.
- **Geometry.** Metres and degrees, +Y up, the front facing +Z. The mounts form one tree rooted at the shell (RG1); every framed box stays in view at spec 002's six aspects (RG5); each selectable keeps an exclusive core of at least 44 × 44 CSS pixels at every supported stage, in 3D and in 2D (RG6), except a side-wall selectable, every member mounted directly on the shell's `left-wall` or `right-wall` anchor, which is list-only wherever its core can't fit; `room:report`'s Side-wall section lists where; each readable face stays at or above the legibility floor on both reference stages (RG7), except a face whose regions are all bound to the turn-cost signal, the neon sign's counter faces, which may fall under it on the reference phone alone, since "Around the room" carries their figures, and the report marks them exempt there.
- **Words.** Every string passes spec 002's C9, so no "Do not claim" phrase of the corpus, nothing the surname rule refuses, and no private-denylist phrase appears (RT2); no UI word holds a digit outside a slot (RT3); a closed-list UI word keeps exactly its slots (RT12).
- **Budgets.** A piece's budget stays at or under `main`'s caps, or FR-053's starting figures while `main` has none (RK1). Agents never raise a cap.
- **Unmeasured figures.** A size, an anchor, or a mount not measured yet carries `estimated: true`, so its work order and the photo guide ask for the measurement (FR-002, FR-026).

A finding prints as `<rule> <file>:<path>: <reason>` (contracts/room-data-files.md §14), and the rule's family says where to look: RD shape, RI identity, RG geometry, RS switches, RT words, RV drawings, RX the model's fit, RK budgets, RL the live configuration, and RW, spec 008's, the highlight.

## Move a piece

Change its placement's `mount` in `scene.yaml`: `on`, the placement it mounts on; `anchor`, one of that placement's piece's anchors; `offset`, in metres in the anchor's frame; and `turn`. Everything mounted on the placement moves with it, in 3D and in 2D. Mark the mount `estimated: true` until its position is measured. A move can change what the camera frames, or bring one selectable's core onto another's, so RG5 to RG7 decide whether it stands.

On a side wall, mount the piece directly on the shell's `left-wall` or `right-wall` anchor. Each turns a quarter about Y, so its `offset` reads along the wall: on the left wall +x points toward the back wall, and on the right wall toward the open front; y is the height above the floor; z is the distance out from the wall. A piece hung there flat, its mount turned about z alone if at all (not about x or y) and out from the wall by no more than its own depth, is on the wall; RG6 then counts its selectable as a side-wall selectable if every member hangs so, and leaves it to the "In the room" list at any stage where its core can't fit, rather than refusing the scene. The anchor itself must stand on the shell's bounds' left or right edge, within 1 mm, at that quarter turn. The photo guide asks for a side-wall piece's origin from the back wall, above the floor, and out from the wall, as it is measured.

## Add a piece

1. **A catalog entry,** `catalog/<piece>.yaml`, its stem the new ID: `name`, the work order's and the report's, 1 to 60 characters; `size`; `stylized_scale`, 1 to 4, which lookdev sets for a readable prop; `origin`, the point on the dimension sheet and the expected bounds that hold it; the `anchors` others mount on; any `live_faces` and `glows`; `standin`, at least one shape of the closed grammar, inside the bounds; `drawing`, `{from: standin}` or primitives; `budget`; and `work_order` (`method`, `shots`, `measurements`, `studio_notes`), which the reviewer reads as room text: it locates nothing, names no third party's marks, and asks the studio for no photo, fetch, or upload (FR-014). Leave `model` out until the Author's file is set.
2. **A placement** in `scene.yaml`'s `placements`, mounted on another, with `frame: true` where the camera should keep it in view, and `label: label.<name>` for its stand-in's label, its word in `ui-words.yaml`. A label word no placement, face, or switch references is refused (RI11).
3. **A selectable,** to make it selectable, in `selectables`: `id`, permanent, since it is the usage event's ID and the conversation's feature; `name`, the list's button, 1 to 40 characters; `members`, framed placements, each in one selectable at most; and `action`, `{talk: {topic, lead}}` or `{resume: {}}`, the `lead` optional, one line of at most 120 characters, published only in `config/room-topics.yaml`. `emblem`, optional, names the conversation panel's emblem from `src/room/hud/icons.ts` (`board`, `wheels`, `screen`, `slate`); none, or a name it doesn't draw, gives the speech glyph (spec 018, FR-005). The order of `selectables` is the list's, the Tab order's, and the loading order's. A room holds 64 selectables at most.
4. **A topic,** if the selectable opens a new one, in `topics.yaml`: `id`; `phrase`, 1 to 60 characters, which fills the fixed message "can't talk about {topic} yet"; `words_from`, the Author's words the topic came from, each quote verbatim in an intent file (RT9); and `corpus`, paths of the form `corpus/NN-<topic>.md`. The corpus files are the Author's to write; until the twin's spec marks the topic ready, selecting the piece shows the fixed message and calls no model.
5. **Generate.** The piece gets its work order, the selectable its ID in `config/room-events.yaml`, which the gateway accepts from its next start, and the topic its mapping in `config/room-topics.yaml`. Until its model arrives, the piece shows its labelled stand-in.

## Remove a piece

Delete its placements, its catalog entry if no other placement uses it, its label words, and its selectable. Add each removed ID to `scene.yaml`'s `retired[]`, with the `kinds` it had (`piece`, `placement`, `selectable`, `topic`), the date as `YYYY-MM-DD`, and a one-line `reason`. RI3 refuses any later piece, placement, selectable, or topic that takes a retired ID, so `retired[]` only grows. The selectable's ID leaves `config/room-events.yaml` at the next generate, and its dashboard series keeps its history; `room:generate` removes the piece's work order.

## Regroup pieces

Change a selectable's `members`. Its pick area is the union of its members' boxes with an exclusive core centred on it (RG6), so regrouping pieces that stand side by side usually needs a move too, until each core is clear of the others' members and areas.

A selectable whose members all hang on the side walls, as "Move a piece" says, is a side-wall selectable: list-only wherever its core can't fit, picked wherever it can. Of two such selectables whose cores overlap only each other's core, the first in `selectables` keeps its pick area and the list reaches the other. A selectable with members on a side wall and elsewhere isn't side-wall, so RG6 holds it to the full rule; another selectable's core over a side-wall member is refused at any stage.

## Retarget a selectable

Change a selectable's `action.talk.topic`, and its `lead` if it has one. Its ID, its usage event, and its dashboard series stay the same.

## Reword

Words are data. A selectable's `name`, a topic's `phrase`, and a UI word in `ui-words.yaml` change in place. Room text in `apps/web/content/room/` is approved by its hash, so a reworded block is a draft, shown only in drafts builds, until the Author approves the new hash. The word checks, RT2 to RT8, hold every reword; the grids a face's words fill are fixed, so a longer word can overflow its region (RT8).

## Change the highlight

The border a targeted piece shows (spec 008, FR-015 to FR-017) is look data: each look's `highlight` gives a `band`, the colour next to the piece's outline, and an `edge`, the dark frame outside it, each a palette name of that look or `#rrggbb`, with their widths in CSS pixels, `band_px` 2 to 8 and `edge_px` 1 to 4. A look that leaves `highlight` out, or any of its keys, takes the spec's defaults: a band of `#ffd23f`, 3 px wide, and an edge 1.5 px wide in the look's ink, its `outlines.color`. RI4 holds both colours to the look's own palette, and RW2 refuses a look whose band and edge both give under 3:1 against any colour of its palette, so one of the two always reads on the room's light surfaces and on its dark ones. `room:report`'s Highlight section gives each look's lowest contrast and the colour it is lowest against. The highlight is drawn in every look and at every quality level, and lookdev's Highlight control shows it on any piece, so the Author judges a change there.

## Add a switch case

A switch in `scene.yaml`'s `switches` places one piece in a pose for each value of the tier: `cases` maps a tier value to a pose. When the piece declares `claims`, every tier value needs its case and there is no `default` (RS1 to RS5). When it claims nothing, a `default` pose covers the values `cases` leaves out, so a case for a value the signal already has is a data edit.

## The HUD and the window

Since spec 005, the room fills the browser's window, and its interface is a HUD of dark glass laid over the scene. None of this is data: the HUD's places are code beside the supported stages, so a data edit can't weaken the checks that run at them.

- **The two layouts.** A window wider than tall and at least 32rem wide takes the column layout: the AI disclosure as a strip at the top, the bar of controls at the foot, and one column on the right, two fifths of the window's safe width between 15rem and 28rem, holding the list above the conversation. Every other window, a phone held upright among them, takes the dock layout: the strip at the top, and the list's strip and the text box's row docked above the bar at the foot, the conversation's log a sheet above them once it holds a line. Where neither fits (a clear area under 304 × 196, a window under 20rem, or a large text size or zoom), the stacked layout keeps the page's old grid.
- **The table, and moving a panel.** Every size is one table, `HUD_PLACEMENTS` in `src/room/compose/hud.ts`: the strip's type and the width bands where its words take two lines, the bar's tiles and their bands, the column's share and bounds, the list's and the text box's rows. `room.css` takes its numbers through CSS properties the room sets on the page's root (`--strip-h`, `--bar-h`, `--column-w`, `--dock-h`, and `--clear-*`), and `test/room/stages.test.ts` pins its HUD rules to them. To move or resize a panel, edit the table; the stages, the checks, and the CSS follow. `test/ui/hud-model.test.ts` holds the bands to the words as IBM Plex Sans measures them, so a longer UI word or a new selectable that needs another row fails until the table gives it one.
- **The clear area.** The room is framed into the window less the docked panels and the safe areas, computed from the table, never measured: one camera draws the whole window, its projection shifted so the room sits in the clear area and the scene continues behind the glass. The clear areas are the supported stages RG5 to RG7 run at; the walking control's box in the clear area's bottom-right corner is the one HUD control RG6 reserves (`reservedBoxes`).
- **The floor.** Every screen of spec 004's sweep gets a stage at least its stage before spec 005, held by a frozen copy of the old formulas, `test/room/legacy-stages.ts`, which nothing may change. A table edit that shrinks one fails `test/room/stages-floor.test.ts`, naming the screen.
- **The caps.** The drawing buffer's ratio is the device's, capped by the quality level's ratio and by its pixel cap (`pixelCap` in `src/room/scene/levels.ts`: 3,686,400, 2,304,000, 1,440,000, and 921,600 device pixels at levels 0 to 3), never below 0.5. Each cap is one edit, tuned from lookdev's window views; the blur behind the glass draws only at levels 0 and 1.
- **Full screen.** Where the browser offers it, the bar's "Full screen" control, or Alt+Enter, puts the whole page in full screen; Escape stays the browser's, so in full screen it leaves full screen first and does what it does in the room only on the next press. A browser that offers no full screen, as an iPhone's, shows no control. The visitor's first entry in a visit sends one `fullscreen_entered` event with no identifier (row V4 of the data-flow disclosure).

## The frame under the HUD

Since spec 014, the room is framed into a frame area between the whole window and spec 005's clear area, so the HUD's glass lies over the backdrop and the room recentres and grows where it can. The area is code, the pieces it protects are data.

- **The ease.** `frameArea` in `src/room/compose/frame.ts` tries the window first, then eases each edge toward the clear area's in sixteenths (`EASE_STEPS`), and takes the first step at which every protected box lies at least `MARGIN_REM` (0.5rem) outside every compact HUD box. The last step is the clear area itself, so a frame always exists and the room is never smaller than spec 005 drew it; a step that throws or isn't finite falls back to the clear area, and the drafts build's frame log says `frame_fallback`.
- **What it protects.** `src/room/compose/protect.ts`: each selectable that is pressable at spec 005's frame keeps a 44 × 44 part of its exclusive core clear of the panels, and both figures keep their framed boxes clear. A step at which such a selectable would be left to the list is refused. Walls, the floor, and the backdrop may lie under the glass. So moving a piece is still a data edit: it may change a screen's ease, never below spec 005's frame, and never with a pressable piece under a panel.
- **The compact HUD.** The boxes the visitor sees are `compactBoxes` in `src/room/compose/hud.ts`, beside spec 005's bands, which stay as the floor's definition: the strip as wide as its words at the top (`strip.maxRem`), the bar's tiles one cluster at the foot's right (`bar.maxRem`), and the column as tall as its content at its band's foot, its log resting at `log.restRem` (8rem, 5rem on short windows) and scrolling. Since the review (T053; the Author's choice of the option labelled "Move the walk control (Recommended)", which put the control in the bar's tile cluster or the column, and the build's choice of the column, plan.md E24), the walking control sits at the column's head, at its right, where the column's band has room above the column's content, so the room no longer eases around it at the clear area's corner; on short windows and phones it keeps spec 008's corner. On landscape windows from 1280 × 720 the always-on boxes cover at most a quarter of the window (`alwaysOnCoverage`). Phones keep spec 005's dock.
- **The checks.** Every supported stage is its screen's frame area, with each HUD box over it reserved for RG6, so RG5 to RG7 run where the visitor sees the room; `npm run room:check`'s report prints a "Frame" line per screen class with its ease. Lookdev's window views frame the same way and record `ease` and `frame_css`.

## The grips

Since spec 014, the resume's sheet sits in the hand at a grip, between the thumb and the fingers, never along the forearm. A grip is data in `scene.yaml`'s `figures.grips`: for an avatar of the room's table and a hand, `right` or `left`, the sheet's held edge's middle in that hand bone's frame (`at`, in the room's metres, each within ±0.15) and its turn from the bone's axes (`turn`, in degrees, each within ±180). RD7 refuses anything else. A hand without a grip takes the default computed from its bones, the midpoint of the hand bone and the middle finger's first bone (`src/room/scene/grip.ts`). The man's and the woman's left grips are estimates, marked so; judge and tune them at lookdev's Hands scene, which shows each listed avatar (`lookdev.yaml`'s `hands.avatars`) holding the sheet in each hand, at rest, in "idle-holding", and mid-walk, with the forearm's 4 cm volume drawn as a wire. Changing a grip is a data edit.

## The path glow

Since spec 014, a glow may follow a path in place of a disc: a catalog glow gives `path`, the points of a polyline in the piece's frame (closed when its last point is its first), and `spread`, the ribbon's half-width in metres at scale 1, at most 0.05, in place of `at` and `radius`. The room draws one additive ribbon along it (`ribbonGeometry` in `src/room/scene/glows.ts`), full strength on the path and fading to nothing at its edge, bevelled at each corner, flickering as the glow's `motion` says, and none at quality levels 2 and 3, as every glow. RD6 refuses a glow with both forms or neither, a path of fewer than two points, or a spread out of range; RG10, a path point outside the piece's bounds. The neon sign's `tube-glow` traces the tube that frames its arrow, spread 0.015 (about 4 cm at the sign's scale of 2.6); its letters keep their own pass. Tuning the path or the spread is a data edit, judged at lookdev.

## The loader and its hints

Since spec 012, a device that draws the room in 3D sees a loading screen from "Enter" until the room is ready: a bar that fills by the first visit's files, over the room's own page, dimmed and held still, with hints below it. The bar and its rules are code; the hints are data.

- **What the bar counts.** Four parts, each a share in `SHARES` (`src/room/loading/progress.ts`), one edit each: the 3D code, 10; the room's text, 2; the faces' typefaces, 3; and the figures' files and the set models, 85, shared by their bytes as served. A file counts once its load has ended (shown, failed after its retry, or skipped), never within it, so the browser's integrity check stays. A model's file joins the bar as soon as its catalog entry sets it; nothing here changes.
- **The ceiling.** The loader gives way at the first of: every part ended, the room in 2D, or `LOADING_CEILING_MS` (7 s) after "Enter", in `src/room/quality.ts` beside `SCENE_WAIT_MS`. A test holds it to at most 7,000, so spec 002's SC-005 holds with the choice screen's 3 seconds; raising it amends that criterion. At the ceiling the room opens with what has arrived, and the rest is shown after the hand-off, as before.
- **The hints.** `hints.yaml`, one at a time below the bar, in its order, a new one every 6 seconds (`HINT_MS`, `src/room/loading/hints.ts`). A hint `by: author` is the Author's words, its `text` exactly the quote its one `words_from` names in an intent; a hint `by: session` names the files its facts come from in `sources`. Adding, removing, rewording, or reordering a hint is an edit here; `when: free_talk_ready` builds a hint in only while the room's build reads free talk as ready.
- **The slots.** A hint states a figure only through a slot, filled at build: `{budget.daily_usd}`, `{budget.monthly_usd}`, and `{budget.fallback_daily_usd}` from `config/budgets.yaml`'s prod, and `{price.input}` and `{price.output}` from `config/prices.yaml`'s last version, its entry for the model of prod's fallback in `config/routing.yaml`. A word of the room's interface a UI word holds exactly is `{ui:<key>}`. So a change to a ceiling, a price, or a control's words changes the hint with it. `test/room/hints.test.ts` pins every other word a hint types in quotation marks to its source.
- **What it sends.** Nothing, but one usage event, `loading_cut_short`, with no identifier, once a visit, when the ceiling cuts the loading short with a file not ended (row V4 of the data-flow disclosure); the dashboard's "Visits whose loading was cut short" graphs it. The bar, the hints, and the controls send nothing.
- **The checks.** RT2 (the "Do not claim" phrases and the surname rule) and RT3 (no digit outside a slot) in every build; RT9 (the Author's quote in its intent) and RT14 (every source in the tree) in strict mode, `npm run room:check`'s; RT15 (the Author's hint his quote exactly), RT16 (at most 160 characters and 25 words, filled); and RT17, a slot that can't be filled, which a lenient build warns of and leaves the hint out, and a strict build refuses.

## The twin's own avatar

Since spec 016, the twin's figure shows the Author's own avatar, `assets/twin/`, the files his intake brings in: its model `twin.glb`, its five clips by role (`idle.glb`, `talking.glb`, `listening.glb`, `greeting.glb`, `desk-lean.glb`), and its 2D still `still.png`. The compositor reads them by those names (`readTwin`, `build/room/avatars.ts`), checks each against `records.json` and main's caps (RA1, RA2, RA4; a file by any other name is RA5's, reported and never served), and bundles them only where main's `assets/policy/approvals.json` approves the model's current SHA-256 with a disclosure line (RA6): the room shows that line beside the twin while its own model or still shows, read from the approval and never copied into data or code. Without it, or where a file fails, the twin's figure shows the stand-in, `figures.twin_stand_in`, with the stand-in line. Everything below is a data edit to `scene.yaml`'s `figures.twin` block or the twin figure's catalog entry, with no source file changed; `npm run room:check` and its report say what each does.

- **Remap the states.** `clips` maps each state, `arriving`, `answering`, `listening`, `resting`, and `present`, to a clip role. By default the greeting arrives, talking answers, listening listens, the lean rests, and the idle is present. Give the lean to `listening`, or the idle to `resting`; RI8 refuses a state or a role outside the lists.
- **Tune the timings.** `rest_after_s`, the quiet before the twin rests (5 to 600, 20 by default); `speak_wpm`, the pace its answer's speaking time takes (60 to 400, 150), within `speak_s`, its bounds in seconds (`[3, 20]`).
- **Tune the lean.** `lean` names the desk's placement in `against`, which RI8 holds to the piece the survey's `desk_corner` names, with `behind_m`, the desk's origin behind the twin's root (0.679 m, the hand-back's), and `right_m`, the desk's top to the twin's right (0.45 m). RA7 measures them from the resolved placements, within 1 cm and 1°, and the report's lean line prints what it found. Moving the desk or the twin without moving the other leaves the lean out (a lenient build) until they agree again; without `lean`, the twin rests in its idle. The scene has no `lean` since the Author's answer of 2026-11-11, "Lean off for now (Recommended)", because the delivered lean bends the right elbow backward (spec 016's plan.md R-19); its line waits in the block's comment, and goes back in with the studio's re-export of `desk-lean.glb`, which comes through a new intake.
- **Move the twin.** The twin figure's placement's offset (its `role: twin`), an estimate until lookdev confirms it, at the lean's spot. Its catalog entry's `size` and `origin.bounds` are the model's measured rest pose (the report prints them), with z extended back by the lean's hip shift; the framing, the pick areas, spec 014's protected boxes, and spec 008's obstacles all read that box. The clips reach past it, so RA8 samples the rest pose and every clip the twin plays every 1/30 s, skinned as three skins them, and refuses a placement whose reach passes a side wall the shell's side-wall anchors stand on, or its back; the report's reach line says how far inside each wall it stays, nearest first (since the Author's lookdev of 2026-11-11, which saw the left foot and hand through the right wall).
- **The still's rectangle.** `still.rect`, `[x, y, w, h]` in metres in the twin figure's frame, `(x, y)` its lower-left corner; by default the box's width, its top at the box's top, at the still's 3:4. The 2D room clips it to the figure's box and keeps its aspect.
- **The texture side.** `texture_px`, a power of two from 256 to 4,096, the twin's own; by default the avatars' `texture_px`, 1,024. RK3 counts the twin's model at it against main's scene cap, so a larger side may need the Author's raise of `scene_texture_bytes` first.
- **The shirt.** The catalog's live face `twin-shirt-lettering` says `surface: model`: the room draws it into the twin's own mesh of that name, never as a quad, with the scene's `print` region naming the outline, `content/room/outlines/twin-shirt-lettering.outline.json`, converted from the studio's sources in `content/lettering/` by `npm run room:lettering`. It is room text: a release build leaves the shirt plain until main approves the outline's SHA-256 with the kind `room-text`.
- **The files' roles.** The model is the twin's picture in 3D; its clips play by state; the still is its picture in the 2D room; the stand-in avatar's files are fetched only once the twin's model has failed, or as the visitor's chosen avatar's.
